# Hexicon VM Plan

Status: draft, 2026-11-18

> The tools this plan names for comparing with the reference (`pp-compare.sh`, `compile-compare.sh`, `suite-compare.sh`, `game-compare.sh`, `tools/reference`, `tools/conformance`, the generators of the VM's tables, and the rest) were removed on 2026-11-24, when Hexicon stopped testing against TADS 3 (language plan, "Retiring TADS 3"). What they established is kept in `tests/programs`, checked by `tools/program-check.py`. Where this plan says that something was checked by them, that is what was done at the time.

## Goal

Build the Hexicon virtual machine in Rust. The first milestone target is running unmodified TADS 3 game images (`.t3` files produced by the stock `t3make` compiler) with output identical to the reference `t3run` interpreter, natively and in the browser via WebAssembly.

The Hexicon compiler comes later. Until it exists, all test programs are compiled with the reference TADS 3 compiler.

Since 2026-11-24, what Hexicon builds is a Hexicon image: T3's layout, with the signature `HX-image` and Hexicon's identifiers for the function sets and the class of the program's objects (`hexicon-gen`, `hexicon-object`; see the language plan, change 0). Running TADS 3 games is no longer a goal, and since step 3 of the break (language plan, "Retiring TADS 3") the VM reads only Hexicon images and saved games.

## Scope

In scope for the VM:

- T3 image loading (all block types defined in the T3 spec)
- The bytecode interpreter (full T3 instruction set)
- Object model: TadsObject, multiple inheritance, property lookup, `modify`/`replace` results as they appear in images
- Core intrinsic classes: String, List, Vector, LookupTable, WeakRefLookupTable, BigNumber, ByteArray, StringBuffer, Iterator, IndexedIterator, AnonFuncPtr, Dictionary, GrammarProduction, StringComparator, CharacterSet, RexPattern, IntrinsicClass, IntClassModifier, StackFrameDesc/Ref, File, FileName, TemporaryFile, Date, TimeZone
- Intrinsic function sets: `t3vm`, `tads-gen`, `tads-io`, `t3test`, regex
- Garbage collection, including weak references and finalizers
- Undo
- Save and restore
- Console output formatting (the `vmconsol` behavior: tag handling, word wrap, paging hooks)

Deferred:

- `tads-net`, HttpServer, HttpRequest, and the WebUI (replaced later by a native browser front end)
- The debugger protocol
- HTML TADS rich output (banners, images, sound). The host interface must leave room for it, but the first front ends are plain text.

Out of scope:

- TADS 2 games

The reference VM is the specification of record wherever the spec documents are silent or disagree with it.

The test suite license allows using it for testing but requires redistributing it complete and unchanged. We do not vendor it; the test harness locates it on disk or fetches it.

`hexicon-vm` has no direct access to files, terminals, clocks, or randomness. Everything external goes through `hexicon-host`, which keeps the VM portable to WASM and makes runs deterministic under test.

## Key design decisions

### Values

A Rust enum mirroring `vm_val_t`: nil, true, empty, integer, object, property ID, constant string, constant list, code offset, function pointer, enumerator, built-in function pointer, and the remaining T3 types. Values are `Copy` and small (target: 16 bytes).

### Objects and memory

- An object table indexed by T3 object ID, as in the reference VM. Object IDs are visible to programs and persist in save files, so allocation must follow the same rules.
- Objects are stored in the table and referenced by ID, not by `Rc`. This fits Rust well and avoids reference cycles.
- Mark-and-sweep garbage collection over the table, with weak-reference handling and finalizer queues matching the reference behavior.
- Metaclass dispatch through an enum of object kinds rather than trait objects, so save/restore and undo can match on concrete types.

### Resumable interpreter

This is the most important decision for WASM. In a browser, the VM cannot block a thread waiting for the player to type.

- Bytecode frames live on an explicit VM stack, not the Rust call stack.
- When the program calls an input function, the interpreter returns `NeedsInput` to the host. The host resumes it when input arrives.
- Some native methods call back into bytecode (sort comparators, `forEach`, `mapAll`). Those callbacks run nested. Requesting input from inside such a callback is an error at first; if real games turn out to need it, we handle it then.

This keeps one code path for native and browser builds, with no Asyncify, no SharedArrayBuffer, and no special server headers.

### Strings

UTF-8 internally, as in the reference VM, with character-index operations done the same way so results match exactly.

### Regular expressions

T3 has its own regex dialect (`<alpha>`, `<nocase>`, `%1` groups, and so on). We port the reference engine's semantics; we do not use the `regex` crate.

### Numbers

BigNumber is a port of the reference decimal implementation (`vmbignum.cpp`, `vmbignumlib.cpp`), not a general-purpose crate, so rounding and formatting match exactly.

### Identity

Hexicon identifies itself as Hexicon. `t3GetVMID` returns `hexicon`, `t3GetVMBanner` returns `Hexicon VM` and the version, and `t3GetVMVsn` returns Hexicon's own version number, not the reference VM's `mjr-T3` and 3.1.3. The number keeps the T3 layout (major in the high 16 bits, then minor and patch in 8 bits each) because libraries take it apart to display it. Neither adv3 nor the system library compares the number against anything; adv3 only shows it for the VERSION command. A transcript that includes VERSION output therefore differs from the reference on that line, by design.

### Save files

Goal: read and write save files compatible with the reference interpreter for the same game image. Fixing the in-memory model early keeps this achievable. If exact compatibility proves too costly, we fall back to a Hexicon save format and document it.

### Determinism

The host provides randomness and time. Under test, both are fixed, so transcripts are reproducible across runs and platforms.

## Testing

1. **Unit tests** in each crate.
2. **Image corpus.** The parser and disassembler must load every `.t3` we can find (compiled tests, adv3 samples, IFDB games) without error.
3. **Conformance suite.** Compile the reference test programs with the reference `t3make` once, then run each image under both Hexicon and the reference interpreter and compare the output byte for byte. The pass count is the main progress metric. `tools/conformance/run.sh` does this; it needs the work directory `tools/reference/run-suite.sh` leaves behind. Both interpreters write UTF-8, so the comparison does not depend on a character set mapping.
4. **Transcript diffs.** Play real games under both `t3run` and Hexicon with the same input script and seed, and diff the output. This covers adv3, adv3Lite, and a growing list of published games.
5. **WASM parity.** Run the same conformance and transcript tests against the WASM build in CI (Node or a headless browser).

Building the reference toolchain natively (`t3make`, `t3run`) is a prerequisite and is part of milestone 0.

Findings from milestone 3:

- A lookup table's entries come back in the order of its storage slots, not in hash order. Slots are handed out in sequence and a freed slot is the first reused. Hexicon reproduces that and uses its own hash function, so the order does not depend on object IDs after all.
- `List.sort` and `Vector.sort` are not stable, and the order of equal elements depends on the exact steps of the reference quicksort, which Hexicon follows.
- The regular expression matcher tries both sides of every choice and keeps the longer match (or the shorter, where the pattern asks). It is a backtracking design with no memoization, as in the reference, so a pathological pattern is slow under both.
- Character classification and upper and lower case use the Rust standard library's Unicode tables. (Classification in regular expressions has since moved to the reference's table; see the milestone 6 findings.) The reference VM has its own, from an older Unicode version. The two agree on everything the suite checks; a difference would show up only with unusual characters. `toFoldedCase` is the exception: it uses a table generated from the reference's (`tools/gen-casefold.py`), since full case folding, where `ß` becomes `ss`, is not in the standard library. Regular expression matching without regard to case still folds one character to one.
- BigNumber's mathematical functions follow the reference's series, working precision, and stopping tests exactly. The last digit of a result depends on all three, so a better algorithm would give different answers.
- An integer calculation that overflows gives a BigNumber of 10 digits, or 20 for a product.
- Byte packing follows the reference step for step, and a side-by-side run of about 300 formats agrees with it, except where the reference's behavior is an accident of how it was built. In those places Hexicon does what the documentation says:
  - The reference never initializes the "up to this many" flag of a group, so whether `(C)3` stops early when values or data run out, and whether it then discards the remaining arguments, depends on what was on the stack. Hexicon treats a group's count as exact unless it has a `*`.
  - Unpacking big-endian UCS-2 text (`w>`) leaves the first character's bytes swapped in a reference built with a 16-bit `wchar_t`, and unpacking null-terminated text sign-extends bytes over 127. Hexicon unpacks both correctly.
  - Converting a BigNumber with more whole digits than it stores (`1.0e20`, which stores two) to an integer gives the stored digits (10) in the reference. Hexicon reports an overflow.
  - The reference crashes on a `/` with nothing before it and on packing some integers with `k`. Hexicon reports a format error for the first and, for the second, writes what the reference's encoding would.
- Two oddities of the reference are kept because a program can see them in its data. Packing an integer with `k` drops bits 28 to 30. `ByteArray.digestMD5` on a range that crosses a 32K boundary hashes the first part again instead of going on.
- Hashes are written with capital letters.
- The character set tables are the reference's own, all 43 of them, embedded in the VM as one 170K file that `tools/gen-charmaps.py` builds. A table also says how to stand in for a character its set lacks (`à` becomes `a` in ASCII). The reference has two more maps built in, for names that match no table: a plain `ascii` with different stand-ins from the `us-ascii` table, and a Latin-1 with none, used for `l1`, `cp819`, and `iso-ir-100`. Those are embedded too, so each name gives the same bytes as it does there.
- `CharacterSet.isMappable` is nil for every character in UTF-16, as in the reference, whose UTF-16 mapping never answers otherwise.
- Mapping bytes to text as UTF-8 leaves off a character cut short at the end. The reference leaves room for it in the string and never fills it in.
- The three random number generators give the same numbers as the reference from the same seed, and a saved state has the same bytes. String templates use random numbers in the same order, including for pieces that produce nothing.
- A callback called by an intrinsic method sees the named arguments passed to that method, as in `lst.forEach(a: 1, {x, a: : ...})`. The VM finds them from the instruction that called the method, so a native call records where its arguments were on the stack.
- `sprintf('%r')` writes 40 as `xxxx`: the reference's table of Roman numerals has no entry for forty. Hexicon keeps that, since a program can see it.
- An anonymous function is stored like a vector but is not list-like. Code that treats "anything list-like" as a list must not unpack one.
- `String.match` returns a length in bytes, not characters, when it succeeds. `rexMatch` returns characters.
- The random number generator is ISAAC, started from a fixed state. A real run seeds it at startup; `hexicon run --norand` leaves it unseeded, which is how the conformance tests get repeatable output. Under `--norand`, a program's own `randomize()` gets the same seed every time, too, so that a game that reseeds at random also plays the same on every run. The reference's `-norand` reseeds such a game from the system, so it differs from run to run there.
- A program's first argument is the image's file name without its directory.

- Milestone 4: done (2026-11-18). Undo; garbage collection, with finalizers and weak references; saving, restoring, and restarting; and the parser classes StringComparator, Dictionary, and GrammarProduction. 108 of the suite's 132 runnable programs match the reference. `GrammarProd.addAlt` compiles its rules with the dynamic compiler, and came with DynamicFunc (2026-11-22). The milestone's test of playing an adv3 game to completion waits for input, which is in milestone 5.

Dates are parsed from text in about fifty formats, written by format strings, compared, and added to, in any time zone of the zoneinfo database or one described by an offset or a POSIX-style string. 122 of the suite's 132 runnable programs match the reference; the ten that do not all need the dynamic compiler. The adv3 sample game plays through a script of about a hundred commands with the same output as under the reference, including undo, saving, restoring, restarting, and a transcript, and each VM restores the other's saved game. Banner windows came later, in milestone 7. In plain mode there are none, as in the reference's plain console, so a program learns from `bannerCreate` that it cannot have one; and long output is not paused a screenful at a time.

The sample game gives the same 688 lines through the WebAssembly module as through the command-line program, for a session with saving, restoring, undo, and restarting; and the page, driven in Chrome with no window, plays the game, takes commands, and keeps a saved game in the browser's storage. Still to do: try the page and the terminal by hand, and in other browsers; and decide where the page and its build are published. Findings from milestone 6 so far:

- Input in milestone 5 was written to block, which a browser cannot do, so it was reworked to the plan's design. The host answers a read with text, the end of input, or "not yet". On "not yet" the VM leaves the instruction that asked unfinished and returns to the host with its frames in place; `Vm::resume` runs the same instruction again. `Vm::run` remains for a host that can wait. A pause works the same way: the host says the time has not passed, and wakes the VM when it has.
- Running an instruction again is only right if everything it did before asking does nothing the second time. Flushing output and finishing off an input script are like that already. A prompt is not, so a dialog, a file prompt, and the More prompt each remember that the question has been asked. An argument count from a `varargc` prefix, and a function pointer that a call took off the stack, are put back.
- A program can only stop between its own instructions. Input asked for from inside a call the VM is making on the program's behalf, such as a sort's comparison function, is refused on a host that cannot wait. The adv3 library never does that in the sample game: a run with a stop and a resume at every read gives the same output as one that blocks. `HEXICON_TEST_SUSPEND=1` makes the command-line program run that way.
- One case is cut short on a host that cannot wait: when an event script supplies a file name that needs the player's confirmation, the script is stopped instead of the player being asked.
- The browser's files are kept in memory by the module and stored by the page in the browser's local storage, under the game's file name. There are no folders. The page passes the browser's time zone name to the module, and the clock is the browser's.
- The module is built with `wasm-bindgen`, whose crate and command-line tool have to be the same version, so the crate's version is pinned. Its generated bindings are unsafe code, so `hexicon-wasm` is the one crate that does not forbid it; it has none of its own.
- The page shows the game's text as the console formats it: plain text in lines of at most 80 columns. A narrow window scrolls sideways. Making the width the page's own is part of the display work that banners and the status line also wait for.
- The width of the console is the host's to say. A terminal reports its window's width and the page reports how many characters fit across it, up to 80; a host that says nothing gets 80 columns, which is what tests and the conformance suite run with. The width is read again each time the player is asked for input, so resizing a window changes the text that follows and leaves what is already shown alone.
- Pausing at a screenful is the host's business, not the VM's: the VM only tells the host when input came from a script, so that the host can start counting again. The command-line program pauses with `[More]` when a screenful has gone by since the player last typed, where Enter shows one more line and any other key the next screenful. It does this only when both its input and its output are a terminal; `--nomore` turns it off, and `--plain` turns off everything a terminal adds.
- The command-line program reads single keys in a terminal, so "press any key" means that. This and the window's size need the `crossterm` crate, which is the command-line program's only dependency outside the workspace. A key is read in raw mode, which lasts only as long as the wait; Ctrl+C during it ends the program.
- The page does not pause output. Text that is longer than the screen is shown from its start, with a More button, and Page Down or the space bar read on; a key pressed while there is unread text below shows more of it instead of going to the game. A click or tap is a key where there is no keyboard.
- A terminal has no good place for a status line: a fixed top row either costs the terminal its scrollback or overwrites text. The command-line program does not show one yet.
- A resource that is not in the image is looked for as a file in the image's folder, as in the reference. All Hope Abandon depends on it: it saves the game to a file and reads the file back as a resource, for its RETRY command. The reference checks the name against the working folder first, so there it works only when a game is run from its own folder; Hexicon always looks beside the image.
- A saved-game file too short to hold the signature is reported as a file that could not be read, as in the reference, and not as a file of the wrong kind.
- In regular expressions, what kind of character each one is (letter, digit, space, punctuation) now comes from the reference's own table, through `tools/gen-chartype.py`, as case folding already did. The standard library's idea differs where a pattern can tell: to the reference, symbols such as `>`, `+`, and `$` are not punctuation. According to Cain showed it: its pattern for turning a straight apostrophe into a curly one looks for a letter, digit, or punctuation mark before the apostrophe, and in `<i>Indagator</i>'s` the character before is `>`. Upper and lower case conversion, and the console's handling of letters, still use the standard library.
- Eight published games were replayed under Hexicon and the reference with the same scripts, and every one gave identical output: Return to Ditch Day (a walkthrough to a win with every point, 7,106 lines), All Hope Abandon (its walkthrough to an ending, 3,868 lines), Square Circle (its walkthrough to a win, 1,703 lines), Mrs. Pepper's Nasty Secret (a walkthrough to a win with every point, 1,688 lines), According to Cain (a walkthrough to the end, 3,744 lines), and about forty exploratory commands each, with saving, restoring, undo, a transcript, and restarting, in The Elysium Enigma, Blighted Isle, and Under the Cognomen of Edgar Allan Poe. None of them needed the dynamic compiler on these paths.
- Games that open with "press a key" need an event script to replay, since a command script only supplies lines; and the reference has to be run with `-nomore`, or it stops at a More prompt for a real key once a script's keys run past a screenful.
- When an event script supplies a file name, the reference checks whether the file exists against the working folder, although the file itself is read and written in the game's folder. Hexicon checks where the file will actually be. The two agree when a game is run from its own folder.
- Hexicon took about twice as long as the reference on these replays; see the milestone 7 findings for where that stands.

Findings from milestone 5:

- The host supplies input as whole lines and as single keys, and the VM does the rest: scripts, logs, and echoing are the same on every host. The command-line host reads standard input, where a key is the first character of a line, and an empty line is Enter. `hexicon run -I file` reads a command script first, as the reference's `-I` does.
- A side-by-side run of every console function that does not need a live keyboard gives the same output as the reference, with and without a script supplying the input, and the same transcript, command log, event log, and log console files. The differences are the three below and the names of the system and its character sets.
- The host cannot interrupt a read, so a read with a timeout reports that timeouts are not available, as the reference's plain console does. Under the reference, that leaves the read marked as in progress until the next one, which changes when the transcript gets the line; Hexicon keeps the same bookkeeping.
- An input script is read the way the reference reads it, oddities included. In an event script a blank line swallows the line after it. Link events are written to an event log as `<href>`, but the reader does not know that name, so they are skipped on playback. A tag given to `logInputEvent` with its angle brackets is written with one bracket too many.
- At the end of input with no script, the reference's test build returns garbage from `inputKey` and `inputEvent`, or waits forever on a real console. Hexicon returns the key `[eof]` and the end-of-file event.
- `inputDialog` asks its question in text, as the reference's plain console does: the prompt, the buttons with their shortcut letters, and a line of input that has to pick one. The line is read like any other, so a command script can answer. At the end of input the result is 0, which is no button.
- `systemInfo` describes a console of plain text, with the reference's answers. The version it reports is Hexicon's, and so is the system name. Every character set name it reports is `utf8`, because text crosses the host boundary as UTF-8.
- Text shown in status-line mode is formatted apart from the main window, kept out of the transcript, and handed to the host when the mode ends. The command-line host has no status line and drops it, as the reference's plain console does.
- There are no banner windows: `bannerCreate` returns nil, which is how a program learns that, and the other banner functions reject every handle.
- Log files are written with plain newlines on every system. The reference writes them through the C library's text mode, so its files on Windows have carriage returns.
- The zone database is the IANA zoneinfo data as the reference's tools compile it, so zone histories and rules are the same data. `tools/gen-timezones.py` converts the reference's `timezones.t3tz` into Hexicon's own layout, which the script describes, and the VM embeds the result, `crates/hexicon-vm/data/timezones.bin` (264K). To take in newer zoneinfo data, build the reference's file with its tools and run the script again. A zone is looked up in the database the first time a program names it.
- A side-by-side run of about 760 lines of zone queries, date constructions, parses, formats, and arithmetic gives the same output, down to oddities a program can see. `getClockTime` returns a zero, the hour, the minute, and the milliseconds, not the hour, minute, second, and milliseconds it is documented to. A POSIX-style zone string has its offset taken as east of UTC, so `EST5EDT` is five hours ahead. A rule on a fixed day of the month describes itself as `INVAL(...)`, and one for the last weekday on or before a day prints the day as the letter `d`. Weekdays before the year 1 come out negative, and name the first day in the list. A fraction of a second is only read if a digit follows its first character.
- Three things the reference does are not matched. A custom date format given as one string, not a list, makes it loop forever; Hexicon tries the format once. A zone made from a POSIX-style string with day-of-year rules reports a weekday from memory the reference never set; Hexicon reports zero. And `setLocaleInfo` returns a value the reference never sets; Hexicon returns nil.
- The local zone is a zone object of its own even when the database has the same zone under the same name, as in the reference, where it shows: `parseDate` reports a zone that the text named even if it is the local one, and an abbreviation such as `CST` is resolved by the local zone's country, not by the local zone itself.
- The host says what the local zone is by its zoneinfo name. The command-line host takes it from `TZ`, or asks the system: `tzutil` on Windows, whose answer goes through the Unicode CLDR table of Windows zone names that the reference uses, and `/etc/localtime` or `/etc/timezone` elsewhere. With no name, local time is UTC shifted by whatever offset the host reports.
- A time zone object read from an image or a saved state carries the offsets and abbreviation recorded with its name, and is looked up once loading is done. If the name means nothing to this VM, the recorded offsets stand in for the zone.
- `getTime` and `toString` of a Date use the local zone. The file times that `getFileInfo` reports are Dates.
- A file name is in one syntax on every host: parts separated by `/`. That is what the reference calls the universal syntax, and it keeps names in the local system's instead, so on Windows it shows backslashes where Hexicon shows slashes. The command-line host translates when it touches the file system. A name is absolute if it starts with `/` or a drive letter. Combining names works out `.` and `..` the way the reference does, which a side-by-side run of path operations confirms apart from a few trailing-slash cases where the reference's answer comes from Windows.
- An open file is held in memory whole: opening reads it from the host, and closing writes it back if it changed. The host's part is reading and writing whole files, which a browser can supply. A file left open is written back when the collector frees its object or the run ends, and before anything else looks at the file system, so a program that opens a file twice sees its own writes.
- A newline written to a text file is written as the system's line ending, as the reference writes it: two bytes on Windows, one elsewhere. Return to Ditch Day writes a file during preinitialization and bundles it as a resource, so its image depends on this. Text files are UTF-8 unless the program names a character set, where the reference uses the system's default character set. Reading takes any line ending, as in the reference.
- The safety levels are the reference's, with its default: a program reads and writes only in the sandbox folder, which is the image's folder unless `--sandbox` names another. Where a file is in relation to the sandbox is the host's to say, since only it knows the real file system. Special files, temporary files, and files the player picked in a file dialog are exempt, as in the reference.
- `setFileMode`, `createDirectory`, and `removeDirectory` return whatever was in a variable the reference never sets: in a test, a string from an earlier exception, and the FileName itself. Hexicon returns nil.
- `getFileType` and `getFileInfo` are documented to take an argument for following links, but the reference rejects any argument. Hexicon rejects it too.
- The reference's plain console asks for a file name, and for the answer to a dialog, as a line of input like any other, so a command script supplies the answer: SAVE followed by a line with a name saves under that name. Hexicon does the same. The reference checks a name that an event script supplies and has the player confirm anything doubtful, and so does Hexicon; the warning it then reports to the program is always nil, as in the reference.
- The settings file that adv3 games share is in the user's configuration folder: `%APPDATA%\Hexicon` on Windows, and `$XDG_CONFIG_HOME/hexicon` or `~/.config/hexicon` elsewhere.
- A BigNumber written to a data file has a byte of flags that the reference fills from memory it has not set: the same program wrote 0x00 in one run and 0x10 in the next. Hexicon writes the flags the number has.
- The console treats only horizontal white space as a place to break a line. It had been using a wider test that included U+0085, which the file packing test showed up.

Findings from milestone 4:

- Undo keeps a copy of each object the first time it changes after a savepoint, and puts the copies back. The object table makes the copy when it hands an object out for modification, so every kind of change to every kind of object is undoable with no code at the places that make changes. The reference instead records each changed property or element, in a fixed space of 65,536 records, and drops the oldest savepoints when that fills. Hexicon keeps up to 255 savepoints, as the reference does, and has no other limit, so a program that changes a great deal between savepoints can undo further back here than there.
- The collector frees IDs lowest first, and a freed ID is the next one handed out, so after a collection new objects take the highest free IDs first. Hexicon follows that, because a program can see IDs: `firstObj` and `nextObj` go through objects in ID order.
- For the same reason, Hexicon creates the same number of objects as the reference for the same operation, including ones that look wasteful. Arithmetic or a comparison between a BigNumber and an integer first makes a BigNumber of the integer. `toString` of a list makes a list of its elements as strings before joining them, while displaying the same list does not. Concatenating a number onto a string converts it without making a string, while `concat` makes one. A probe of about 150 operations creates the same number of objects under both.
- The reference collects before creating an object once 10,000 have been created since the last collection, or more than 6 MB allocated. Hexicon collects at the same points. Which objects a collection frees decides the numbers later objects get, and preinitialization writes those numbers into the image, so matching the reference's image needs the same collections at the same times.
- The 6 MB are what the reference asks its heap for, in its own layouts in memory, which depend on the machine; Hexicon counts what the reference built for 64-bit Windows asks for (`heap.rs`). A program-defined object is 40 bytes, 16 for each superclass, 8 for each hash bucket and 40 for each property it has room for, with the reference's rules for both: room for 16 properties when made with `new`, as many as it has when loaded or cloned, doubled when full, or half again past 128. A list is 2 bytes and 5 for each element; a string 2 and its bytes; a vector 4, 5 for each element it has room for and one more, rounded up to 8; a lookup table 32, 8 for each bucket and 40 for each slot. Growth counts the new size, and counts it a second time when the block no longer fits the cell of 32, 64, 128, 256 or 512 bytes it was in, because the reference's heap then allocates a new block and counts that too.
- Several intrinsics make their result before they call back into the program, or make it larger than it ends up, and Hexicon does the same, so that the objects get the same numbers and the bytes counted are the same: `mapAll` and `subset` on a list make a copy of the list first; `findReplace` and `rexReplace` make the result string at the first match, with room for three times the subject, growing by what each piece needs and 512 more, and give back room only if 256 bytes or more are unused; `split` makes its list as long as its limit, or the number of pieces of the given length counted in bytes, or 10, and lengthens it one element at a time after that; the parser's lists and `getGrammarInfo`'s are made at their full lengths.
- An intrinsic method that creates several objects creates them in the reference's order, so that each gets the same number: `String.split` creates the list first and then the pieces, for one, and the table of macros makes each macro's name, then its list, then its expansion, then the list of its parameters and their names. A collection in the middle sees the same objects either way, but it frees different ones if their numbers differ.
- Saved states are in the reference's format, and each VM restores the other's: a program that saves one of every kind of object so far gives the same output from all four pairings of which VM saved and which restored. Three things made that work. A weak-reference table is saved without a default value, because that depends on the version of its own class, not the plain table's. A table's chains are saved as they are, so the two VMs have to hash keys identically. And the reference can write a first-free-slot link that points outside a copied table, which Hexicon reads as no link.
- So lookup tables use the reference's hash function exactly. It has two oddities a program can see. An integer hashes to the product of its 16-bit halves, which is zero for anything under 65,536. A BigNumber hashes by its digits, so one that equals an integer key is not found under it. And because objects hash by ID and keep their chains across a restore, a table keyed on an object the program created does not find that key after restoring. Hexicon behaves the same in all three.
- Using the same hash also settled the last differences in how many objects are created: a lookup compares the key it wants only against keys in the same bucket, and comparing a BigNumber with an integer creates an object.
- To restore or restart, the VM needs each image object as it was loaded. The object table keeps a copy the first time one is changed after loading, by the same hook undo uses, instead of keeping the image.
- A file name a program gives is relative to the folder its image is in, as in the reference, not the working directory. That is the command-line host's choice: the VM hands the host a name and takes back bytes.
- A saved state carries the image's file name. The reference writes the full path it was run with, and Hexicon the path it was given.
- A dictionary stores its words as the reference does: 256 buckets by the comparator's hash, the newest word first in each, and within a word each entry after the last one for the same part of speech. The order of `findWord` results, of `forEachWord`, and of spelling corrections all follow from that, and a side-by-side run of about 500 lookups, corrections, and listings under seven comparators gives the same output.
- With a comparator the program wrote, the reference calls its `calcHash` twice to add a new word and twice to remove a word's last entry. Hexicon makes the same calls, since the program can see them.
- A StringComparator matching a dictionary character that stands for several input characters keeps comparing against the first input character, so the later ones only ever match through the case-folding comparison, and the result says the match ignored case when it did not. Hexicon does the same.
- The grammar parser explores alternatives in the reference's order, which fixes the order of the results and of the match objects created for them: a side-by-side run of 50 sentences through a grammar with left recursion, fallback alternatives, and token types agrees on every tree and on the IDs of the objects.
- For an alternative that is only `*`, the reference reports the last token index from memory it never set. Hexicon reports an empty range, with the first index past the last.
- The reference writes a malformed saved state if a dictionary word's only objects are transient: the word goes in without its count. It then fails to restore that state. Hexicon leaves such a word out. The reference also crashes restoring a state in which a dictionary from the image had changed, in a test here; Hexicon restores it.
- A grammar production from the image is never saved, in the reference or here, so alternatives deleted from one come back on a restore.
- While an intrinsic function or method is in the middle of its work, it can hold objects nothing else refers to yet. The reference keeps those on the VM stack. Hexicon treats every object created since the instruction began as reachable for that collection, which keeps a little garbage until the next one. When the call runs program code (a callback from `forEach`, or a constructor from `new`), what that code created and dropped is garbage, as in the reference: Hexicon keeps only what the intrinsic made before the call and what each call returned to it, until the intrinsic's instruction is over.
- A vector keeps the room it was created with, or has grown to, as the reference does, because the image written after preinitialization records it: 10 elements for `new Vector()`, the number asked for otherwise, and room the reference's growth rules give it as elements are added.
- A stack trace asked for frame references gives each level of byte code a StackFrameDesc: a place in a call, with the scope of the code there. It refers to the call's StackFrameRef, which a frame has one of at most, made the first time it is asked for. While the call runs, the variables are read and set on the stack; when it returns, they are copied into the StackFrameRef, which keeps them, and the method context, from then on. A StackFrameDesc is indexed by a variable's name, and a StackFrameRef by its number among the locals and then the arguments. Both are saved and restored in the reference's format; a call that is running when the game is saved is saved as if it had returned. A frame in code compiled while the program runs is reported as its DynamicFunc.
- `GrammarProd.addAlt(rules, matchObj, dict?, symtab?)` compiles the rules, alternatives as a `grammar` statement has them before its colon, against the names in the symbol table, and adds each to the production, made with the match object given; each word in a rule goes in the dictionary under `miscVocab`, with the production as its object, and the match object's `grammarAltProps` is made again. A name that is no production of the program, or no property, is an error, which the program gets as a `CompilerException`. As in the reference, an enumerator in such a rule need not be declared with `enum token`, and `*` cannot end one, since nothing but `|` or `:` may follow it.
- A DynamicFunc is a function compiled while the program runs. Its code goes after the program's own, at an address of its own, so that it runs like any other function, and the VM's copy of the code grows by it; an instruction that runs on past the copy the interpreter took takes the code again. A DynamicFunc in an image or a saved game is the length of its code, the number of objects it refers to, its method context, its source, the code, and where in it each object's number is, as in the reference, and its code is put after the program's when it is loaded or restored, the numbers of the objects in it fixed up as any other references are. What its code refers to, its source, and its method context keep it in use. A method bound to one, as an object written in such code has, is code to `propType`, as one bound to an anonymous function is.
- A string buffer keeps its room and the step it grows by for the same reason: 256 and 256 for `new StringBuffer()`, the size asked for with a step of the same up to 256, half of it up to 4096, and 2048 after that, both at least 16. It grows to the length it needs, rounded up to a whole step, and undoing a change does not give room back. Before this, a string buffer in an image was not loaded at all.

Findings from milestone 2 that later milestones depend on:

- The stack limit is observable. The reference VM allows 4,096 slots and spends 11 on every call; Hexicon keeps frames elsewhere but counts the same way, and a runaway recursion stops at the same depth under both (checked at 336 and 252 levels for two different functions).
- A constructor returns `self`. The `new` instructions rely on that to deliver the object; the VM only supplies it when a class has no constructor.
- An exception table's ranges are tested against a caller's return address, not the address of its call. The compiler makes each range run past the call.
- Catching an exception does not trim the stack. Whatever the function had pushed stays until it returns.
- A return to an address holding `getr0` performs the `getr0` as part of the return.
- The `inc` instruction does not check for overflow, though `dec` and the others do.
- When the VM creates a `RuntimeError`, it reads each message parameter's type from the slot before it, so the constructor only receives a parameter intact if it has the same type as its predecessor.
- Object IDs for new objects come off a free list that starts at the top of the newest 4,096-entry page. Hexicon reproduces the order, but not the exact sequence of temporary objects the reference VM allocates, so IDs can still differ. Nothing found so far makes that visible to a program other than the test-only `t3test` functions.
- Intrinsic class methods are found through the property lists in the image's metaclass table, and an intrinsic class inherits the methods of the one it derives from (a list has `createIterator` from Collection).
- The console drops newlines that follow a newline, and anything that would start the output with a blank line. Blank lines have to be asked for.
- The text a value is given when nothing better is known, `object#12`, `property#5`, `function#1f`, `enum#3` or `builtin#1.2`, has a null character at its end: the reference counts the byte that ends the text it formats as part of the string. A program can see it, in the string's length or when the text is joined to more. Hexicon's strings have it too. (Found when one of the compiler's test programs printed an object.)
- There are two conversions to text, and they differ. Where text is simply expected, as when a value is displayed, written to a file, or passed to `concat`, only a string, an integer, `nil`, `true`, a list, or an object converts; the address of a function or a property, a value of an enumeration, and a built-in function are errors ("cannot convert value to string"), in a list as much as alone. Asked for outright with `toString`, or as the right side of adding to a string, each of those has a name (`function#1f` and so on), and the elements of a list are converted that way too.
- An anonymous function that carries anything with it is a vector underneath, of its code's address and what it carries, and converts to text as a vector does, though in no other way is it a list: `toString` gives the function's name and then the contents of each context, and displaying it is an error, because its first element is the address of a function. (Found, with the last, when a test program for the compiler displayed one.)

Findings from milestone 7 so far:

- Building with `--features profile` (`cargo build --release -p hexicon-cli --features profile`) gives a VM that samples what it is doing every 20 microseconds and reports where the time went when the game ends: by kind of work (the interpreter, property lookup, each phase of the collector, each built-in function and intrinsic method) and, for the interpreter, by instruction. It needs nothing installed. A sampling profiler such as samply needs Administrator rights and Microsoft's Performance Toolkit on Windows.
- At the start, on Ditch Day's walkthrough, the collector took 26% of the time, property lookup 15%, and regular expressions 8%.
- The collector treats everything the undo savepoints refer to as reachable. The reference keeps 255 savepoints, and Hexicon keeps each object's state from before its first change after each one, which came to 39,000 saved states and over a million references for every collection, 279 times over. The saved states never change, so the VM now counts the objects they refer to as states come and go, and a collection starts from those few thousand. A collection that frees nothing leaves weak tables and dictionaries alone, and one that does only looks for what it freed.
- Property lookup walks the superclasses each time, and adv3's are many. What an object's one superclass gives for a property is now remembered, by superclass and property. Setting a property on an object a remembered lookup depends on forgets that property's lookups; any other change to such an object, an undo, a collection that frees one, or a restore forgets them all, so a lookup always finds what the walk would.
- The regular expression matcher saved its state at every choice in a new allocation; it now keeps the state in place. Patterns given as strings are compiled once and kept, since compiling one always gives the same result.
- What is left is spread out: the interpreter loop itself is about 40% of the time, property lookups 13%, and the collector about 12%, much of that in passes over every slot of the object table, whose objects are kept in place, 128 bytes each.
- `hexicon-fuzz` (its own crate) makes damaged copies of images and saved games: bits flipped, boundary values written over bytes and over the numbers at the start of blocks, stretches cut out or repeated, the end cut off. An image is parsed, loaded, and run with no input; a saved game, given the right length and checksum after it is damaged so that it reaches the reader proper, is restored into a probe program that builds and then walks objects of most kinds. Cases run in child processes, so that one that crashes or hangs costs only its own process, and each is made again from the seed and its number.
- What the fuzzer found, all now errors: code that names a local or an argument the frame does not have, or swaps or reads below the bottom of the stack (`stack access is out of bounds`; the reference reads or writes whatever is there); a call with more arguments than the stack holds; an instruction whose operands run past the end of the code (`invalid opcode`); an object ID in the billions, which would have taken that much memory (an ID may be at most sixteen times the number of objects in the image, plus 65,536, where the programs we have go to eight and a half times); a pool that claims millions of pages; and a list or vector that holds itself, which converting to text or comparing would follow for ever (the reference crashes; a depth of 500 is now a stack overflow, which the program can catch).
- Three were differences from the reference that a sound program could meet as well. A string is at most 65,535 bytes, since its length is 16 bits wherever it is stored, and making a longer one is an error (`string is too long`); Hexicon had no limit, so a string that doubled each time went on until memory ran out. A string buffer can be far longer; turning one into a string has the same limit. An image must have every page of its pools, or it does not load (`loading undefined pool page`), and a pool's pages must be a power of two in size (`invalid page size`).
- The collector's search of what intrinsics at each level of nesting may be holding was a pass over the levels for every object; with thousands of levels it took most of the time. The ranges are now merged once, in order, and each object is a search away.
- Damaged programs can go on for ever, and the fuzzer reports a case that takes more than ten seconds as a hang, with whether it came in reading, loading, or running. Each of the 34 hangs in running was checked against the reference. Some loop under both. In the others an error leads to a cascade: building the `RuntimeError` for it fails, because the damage is in its constructor, and that failure builds another, a level deeper each time, each taking a longer stack trace, until the stack runs out. The reference does the same on its own C stack and crashes; Hexicon keeps going until its stack overflows and the error unwinds every level, which with deep enough levels takes minutes. The rest were the three differences above.
- Published games with walkthroughs are few, but a comparison needs none: any commands will do, since both VMs are given the same ones. `tools/explore.py` plays a game a round at a time, choosing each round's commands from what the game last said under the reference (examining the words it used, trying verbs on what is there, moving the way the text points, looking, undoing, and saying what the parser must refuse), then replays the whole under both and compares. Over a thousand commands a game, the twelve games we have give the same transcripts, apart from the line break after a key press noted below. A command that opens a menu read a key at a time (HINT, ABOUT, HELP, in many games) is left out, since the reference waits for ever for a key once the script runs out.
- The Quest of the Golden Banana (Eric Eve's adv3 tutorial game) is replayed from David Welbourn's walkthrough, written for version 1.4. The game is 1.7, and needed two changes to reach the end: the ghost's question is answered with `ghost, yes`, where `yes` alone now goes to Sarah, and the wait for the bush to burn is seven turns. It ends with 41 of 43 points, the same 4,301 lines under both.
- Gun Mute is replayed from David Welbourn's walkthrough, with one change: the first try to drink the plainswoman's potion is refused until it has charged, so the script drinks twice. It ends with 20 of 20 points, the same 1,567 lines under both. Dead Like Ants is replayed from his walkthrough as it stands, to 6 of 6 points, the same 1,279 lines under both. The Elysium Enigma is replayed from its author's walkthrough for the competition release, which plays the later release we have to its end as it stands: 30 of 30 points, the same 3,527 lines under both. Lydia's Heart plays to its good ending from its walkthrough under both, but like I Am Prey it seeds its random numbers from the clock, so that its flavor text differs from run to run under either, and it is not in the benchmark. The same goes for The White Bull, which plays to its winning end from its walkthrough under both, Leo's idle remarks coming in a different order on each run. Ditch Day's opening screen waits for a bare Enter, which `explore.py --start line:` gives it; explored past it, it is the same over a thousand commands.
- The reference's interpreter on Windows does not use the plain console the suite's `test_exec` does (`os_stdio`), but the console layer for terminals in plain mode (`osgen3` with the DOS keyboard code), and the two differ in two ways that published games, which only `t3run` can be compared on, can show: clearing the screen in plain mode does nothing in `t3run` (Hexicon wrote a form feed, as `test_exec` does), and a key read from input that is not a keyboard is one character of it, so that what is left of the line goes to the next read (Hexicon took a line for each key). Both now match `t3run`. One difference is kept: asked for an event with a time limit, `t3run` answers the end of input, where `test_exec` answers that time limits are not supported, which is what Hexicon answers, since the end of input tells a game to stop.
- Under the Cognomen of Edgar Allan Poe waits on timed events in its opening, and under an event script the reference, given the end of input for each, never gets past it; given its commands as plain input instead (`explore.py --stdin`), it does, and both VMs give the same transcript. I Am Prey seeds its random numbers from the clock, and gives a different transcript on each run under either VM, even with `-norand`; it cannot be compared, and `explore.py` says so when the reference differs from itself.
- After a key press, Hexicon's plain console starts a new line and the reference's does not; the transcripts differ only in those blank lines.
- Banner windows are panes a program divides the screen into, each attached to a side of the main window or of another banner. The reference's plain console has none, and so has Hexicon's plain mode, so nothing compared against it changes. In a terminal and on the page, where there were none either, there now are. Every game we have, adv3 and adv3Lite alike, asks for one at the start and shows its status line in it, the location at the left, the score at the right, and a line of exits under them, where it fell back on the old two-part status line before.
- The VM gives each banner a formatter of its own, as the reference gives each a console of its own: its text is broken into lines at the banner's width, and `<tab align=right>` lines the score up at its right. A text grid's formatter, as in the reference, does not break lines, shows markup as text, and keeps every space. A `<body bgcolor=statusbg>` in a banner's text, which is how adv3 colors its status line, is passed to the host as the banner's background, as the reference's formatter passes it to the display layer.
- How the screen is divided is the host's, and both hosts do what the reference's character-mode display layer does (`osgen3.c`), in one model they share (`hexicon_host::banner::Screen`): each banner takes its space from what its parent has left, in the order of its parent's list, a top or bottom banner the full width and a left or right one the full height; a size is in lines or columns, or a percentage of the parent's; a size given as advisory is ignored, since the size can be made to fit the contents, which is the last line ended, plus one, by the widest column written; and a banner whose parent is deleted stays but is not shown.
- A terminal cannot keep the main window's text to part of its width, so it has no banners at the left or right of the main window (a program is told it cannot have one); inside another banner, any side will do. The main window becomes a scrolling region between the top and bottom banners, which are drawn with the cursor kept where it was. A banner that appears under the cursor moves the text above it up, so that what was being read stays in view, and the terminal is given back whole when the program ends or is stopped. Banner text is drawn when the program flushes it or waits for input, not as it is written, so that a status line rewritten each turn does not flicker. The old two-part status line, for a program that uses it, is a line at the top. Tests drive the terminal through a stand-in that interprets the control sequences, to check what would be on the screen.
- The page lays banners out the same way, in lines and characters, and shows those above the main window in a strip above the text, and those below in a strip below it. A banner in the status line's colors is drawn in the colors of the page's bar.

Findings from milestone 1 that later milestones depend on:

- A method header gives no code length. A function's extent comes from its exception table and debug records when it has them, and otherwise from following its branches and from where the next function starts.
- Release builds carry debug records too, for any function with local variables. The frame tables in them are what `t3GetStackTrace` and the reflection library read.
- Pre-initialized images keep references to static initializer code that pre-initialization discarded. The VM must not treat these as errors at load time.
- The reference compiler emits a `switch` whose default branch points into the middle of an instruction (`rand.t` in the suite). The default is never taken. The VM must not validate branch targets ahead of execution.
- Ten opcodes in the reference interpreter are missing from the instruction set document: `iternext`, `getsetlcl1`, `getsetlcl1r0`, `dupr0`, and `getlcln0` through `getlcln5`.

## The rich display (planned)

What a game shows beyond text: pictures, sounds, links, styled text, panes. TADS 3 had it as HTML TADS, whose markup is HTML 3.2 and TADS's own tags (`<banner>`, `<sound>`, `<tab>`, `<aboutbox>`, `<nobr>`, `<wrap>`, `<bq>`, `<credit>`), with no style sheets at all: a look is written as `<font>`, `bgcolor`, and `align` wherever it is wanted, and the player can change almost nothing of it. The Golden Skull (Hexad plan, 2026-11-27) is the first game to need it.

### Decided (2026-11-27)

- **The display is the web engine**, in a browser and in a downloadable program alike. The program is a window around the system's web view (WebView2 on Windows, WebKit on macOS and Linux), showing the same page as the browser. Hexicon does not lay out text itself.
- **Not HTML TADS's look.** Existing markup has to work, and look reasonable; it need not look as it did in HTML TADS.
- **Styling is open to authors and players**, as a browser's is: an author styles a game with a style sheet, and a player can restyle any game.

The terminal stays a display of text, as it is: the same markup, shown as the plain console shows it.

### Recommended

**A profile, written down.** Hexicon promises a defined set of markup and style, not whatever a browser does, so that a game written for it works wherever Hexicon runs. The profile is a subset of real HTML and CSS, which is what makes the web engine cheap: the page shows it as it is, once it is checked.

- **Kept:** everything HTML TADS has, with its own tags turned into the page's: a banner is a pane, `<tab>` alignment, sounds in their layers, the about box, the title, a More prompt, links, and image maps.
- **Added:** `class` and `style` on any element; `<span>` and `<div>`; `<figure>` and `<figcaption>`; SVG and WebP pictures, besides JPEG and PNG; Ogg, MP3, and WAV sounds; fonts bundled as resources (`@font-face`); and a style sheet for the game, a resource named in the manifest (`stylesheets = ["skull.css"]`).
- **CSS, a listed subset:** colors and backgrounds, fonts (family, size, weight, style, variant), text alignment, decoration, transform, and indent, line height and letter spacing, margins, padding, borders and their radius, widths and heights with their limits, `display` (block, inline, inline-block, none, and flex for a row of things), floats, list styles, and media queries for the width of the window, for light and dark (`prefers-color-scheme`), and for reduced motion. Transitions and simple animations, perhaps later. Not positioning beyond that, not grid, not anything that reaches outside the game.
- **Left out on purpose:** scripts, event handlers (`onclick`), forms, frames, and any address outside the game's own resources. A game's text cannot run code in the page or fetch anything from the network. Everything else is removed before the page sees it, so a game cannot get round the profile by writing markup the profile does not list.

**Hexad's own text, styled by name.** Hexad already marks its text with style tags (`roomname`, `roomdesc`, `roomcontents`, `parser`, `notification`, `assume`, `tip`, `inputline`, `statusroom`, `statusscore`, and the rest). On the rich display each is an element with a class of that name (`<div class="roomname">`), so a style sheet can style the library's text as well as the game's: the room's name, the parser's complaints, the score notices, what the player typed. The class names are part of the profile, and the guide lists them.

**The player's styles.** As in a browser, the player's choices are a style sheet of their own, under the game's in the cascade, except where the player says theirs come first (CSS's `!important` from the player): a font and size to read in, colors or a high-contrast theme, the width of the text, pictures and sounds on or off, links on or off. The page offers the common ones as settings, and takes a style sheet of the player's own for the rest; a setting can be for every game or for one. `systemInfo` answers the player's choices (pictures off is `SysInfoPrefImages` 0), so a game, and Hexad's `Picture` and `Sound`, do as the player asked.

**How it is built.**

- **The VM passes the markup on.** On a rich display the VM does not break lines or flatten tags, as its console does for text: it passes what the game writes, in the order written, to the host.
- **One checker, shared by every rich host** (in `hexicon-host`): it parses the stream, turns TADS's tags into the page's, keeps what the profile lists and drops the rest, and gives the host a document to show. Being shared, the browser and the program show the same thing.
- **The page shows that document**, as elements, with the game's style sheet and the player's. Pictures, sounds, and fonts come from the image's resources.
- **`systemInfo` answers for the display it is on**: HTML, the kinds of picture and sound, panes, colors, and the player's choices.

**How it is tested.** The checked document is written out as text, as a transcript is, so game-check and doc-check can compare it without a browser: The Golden Skull's sign, as a table with its style, its sounds in their layers, its compass as an image map. Headless browser screenshots check the page itself, less often.

The profile was agreed on 2026-11-27.

**Done, 2026-11-27: step 2.**

- **A host can be a rich display.** `Host::rich_display` says what it can do and what the player has chosen (`RichDisplay`); such a host gets what the program writes, markup and all, through `print_markup`, and a line from a script as the player's words through `print_input`. The VM formats nothing for it; a transcript is still formatted as text. `systemInfo` answers for it: HTML, JPEG and PNG, WAV, MP3, and Ogg, sounds over each other, colors, highlighting, the interpreter class HTML, and the player's choices of pictures, sounds, music, and links; MIDI, MNG, fading, and links outside the game, no.
- **The checker** (`hexicon_host::rich::Checker`) reads the stream a character at a time, so a tag or an entity split between writes is read whole. It replaces entities (the VM's table of them is now `hexicon_host::entities`, shared), turns the control characters into the page's (`\n` a line break, `\b` a blank line, `\^` and `\v` the next letter's case, a quoted space a space that stays), and TADS's tags into the page's (`<bq>` is `<blockquote>`, `<nobr>` a span that does not wrap, `<listing>` and `<xmp>` are `<pre>`, `<credit>` is `<cite>`). It keeps only the profile's elements and attributes, and in `style` only its properties, with a `url()` only for a resource; a script, a style element, a frame, a form, and what is in them, go, and so do an `on...` attribute, a picture or a background that is not one of the game's resources, and a link to anywhere but a command. An element outside the profile goes and its text stays. Elements are closed in order however they were written: an end tag closes what was opened inside it, one that ends nothing is dropped, and a paragraph, a list item, a row, or a cell ends the one before it. `<title>`, `<sound>`, `<body>`, `<tab>`, `<aboutbox>`, and `<banner>` are kept for the page to handle. Its 12 tests are in `rich.rs`.
- **`hexicon run --rich`** is a rich display that can do everything, and writes the checked document as text: an element as the profile's markup, with a line ended at each line break, block, and line the player typed (`<kbd>look</kbd>`).
- **game-check plays a script again with `--rich`** where there is a `.doc` beside its `.out`, and compares the document as it compares the transcript. The Golden Skull has one: its compass is a table of image maps with the ways out lit, its sign a table with its colors, its sounds in their layers, and its about box the page's.

What the first document showed, for the steps after:

- **Hexad, told it is on HTML, writes its status line in the stream** as TADS's `<banner id="StatusLine">`, with the room's name and the exits as links and the score after `<tab align=right>`. The page will show a `<banner>` as a pane, and a `<tab>` as its alignment.
- **TADS's named colors** come with it: `<body bgcolor="statusbg" text="statustext">`. The page maps `statusbg`, `statustext`, `text`, `bgcolor`, `link`, `hlink`, `alink`, and `input` to its theme, and the player's.
- **What the player types is wrapped in `<font face="hexicon-input">`**, Hexad's style for input in HTML; and the room's name is `<b>` between line breaks, with blank lines around it that will look loose on a page. Both are for step 5, when Hexad's style tags become classes.
- Banners made through the banner functions (`bannerCreate`, Hexad's panes), rather than in the stream, still get formatted text on a rich display; they come with the page.

**Done, 2026-11-27: step 3.**

- **Panes are rich too.** On a rich display, what a program writes to a text pane comes to the host as markup (`Host::pane_write_markup`), as the main window's does; a text grid's is still text. Hexad, which prefers the pane functions to the `<banner>` tag, now gives its status line to a pane with its links and its right-aligned score, on the page as in HTML TADS. `hexicon_host::rich::Document` keeps the main window's checker and each pane's, and gives the host what happens in order (`Event`): the main window's items, a pane made, emptied, or removed, and what a pane is to show when it is shown. `hexicon run --rich` writes a pane's as `<pane id="1">...</pane>`.
- **A game's style sheets are its resources whose names end in ".css"**, applied in order; the manifest's `stylesheets = [...]` adds them to the resources, and says what they are for. `hexicon_host::rich::check_stylesheet` holds one to the profile: each rule keeps only the profile's properties, `@media` only the profile's queries, and `@font-face` a font among the game's resources; every other at-rule goes, `@import` with them. Each selector is put under the page's element for the game (`#game`), and `body`, `html`, and `:root` are that element, so a game styles its own part of the page and not the page's. A game's `!important` is taken out, in a sheet and in a `style` attribute, so that only the player can put their choices first.
- **The WebAssembly build is a rich display when the page asks** (`setRichDisplay`, with the player's choices, and `setPlayerChoices` when they change). It gives the page the document as JSON (`takeDocument`), the game's resources by name (`resource`), and its style sheets checked (`styleSheets`). `tools/web-play.js --rich` writes the document as `hexicon run --rich` does: The Golden Skull's is the same from both, but for how a script ends.
- **The page is a rich display by default.** It builds the document as the page's own elements: pictures, backgrounds, and fonts from the game's resources; links and an image map's areas as commands (entered, added to what is being typed, or put on the command line, as `append` and `noenter` say); `<tab align=right>` to the end of its line at the right; `<body>` as its window's colors and picture; TADS's named colors (`statusbg`, `text`, `link`, ...) as the theme's; the about box in a dialog of its own; the title as the window's; the command line where the game's prompt leaves off; and a text pane as tall as what is in it, in the strip above or below the main window. Sounds play in their layers: looping, a number of times, now and then (a chance each second), interrupting, and cancelled; a sound the browser holds back until the player has done something plays then.
- **The player's settings**, in a dialog, kept for every game: colors (the game's, light, dark, or high contrast), font, size, the width of the text, pictures, sounds, music, links, a style sheet of the player's own, and whether their colors and font come first. CSS cascade layers order them: the page's defaults, then the player's, then the game's, so the game's look wins; with "mine first", the player's are `!important`, which wins over the game's sheets and its `style` attributes alike. Pictures, sounds, music, and links go to the game as well (`systemInfo`), so Hexad's `Picture` and `Sound` leave out what the player has turned off. A setting makes the page a display of plain text instead, as before.
- **Checked in Chrome without a window** (`tools/web-check.js`, which now reports the page's errors, and can do something to the page before its picture): The Golden Skull's pictures, its sign's table, its compass as an image map with the ways out lit, the status line, the about box, the settings dialog, and the player's high contrast and monospace coming first over the game's colors and fonts.

**Done, 2026-11-27: the player's files.**

- **A game's files are files**, in a folder the player can find: `Hexicon` in their documents (`dirs::document_dir`, or their home folder), with a folder for each game named after its file without `.hxg`, so The Golden Skull's saved games are in `Documents\Hexicon\skull`. The player writes a file beside its place and then moves it there, so a file is never left half written; what goes wrong it tells the page, which says so. A name a folder cannot have (a slash, a colon, `CON`, a dot at the end) is written with `%` and its code, and comes back as it was; every other name is the file's own. A saved game copied into the folder is there the next time the game is opened.

- **"Saved games"**, a button the player's page has and a browser's does not, opens the game's folder in the system's file manager.

The names and the messages have tests of their own (`cargo test -p hexicon-app`).

**Done, 2026-11-27: the display's leftovers.**

- **Panes at the sides.** A rich display can keep the main window to part of its width, so the page and `hexicon run --rich` allow a pane at its left or right (`Screen::set_side_panes`); a terminal and the page's plain text still say no. The page lays the panes out as a terminal does, in its own measures: each takes its side of what its parent has left, in the order they were made, a pane within a pane included, and the main window has the rest. A pane at a side is as wide as the game asks, in characters or as a percentage, or as what is in it when it is sized to its contents, up to half of what is left; it is in the game's own colors, set off by a rule. A pane at the top or bottom is as tall as what is in it, as before. The WebAssembly build gives the page each pane's parent, side, size, and whether it was sized to its contents (`Screen::layout`), as the game asked rather than in character cells.
- **`<banner>`.** A banner in a game's text is a pane too, after the others: `<banner id=notes align=right width=20%>...</banner>` puts what is in it in the banner of that id, replacing what it had, with its size in percent or pixels, or `previous`; `<banner remove id=notes>` and `<banner removeall>` take banners away. The checker found the first fault: a banner removed has no end tag, and it was held open, so everything after it would have gone into the banner. It is now an element with nothing in it.
- **Hover pictures.** An `<img>` with an `hsrc` shows that picture while the pointer is over it, or while the link it is in has the keyboard's focus, and one with an `asrc` while it is pressed. Hexad's `Picture` has them as `pictureHover` and `picturePressed`, and `pictureCommand` makes it a button.
- **Fades.** A `<sound>` takes a `volume` (0 to 100), and a `fadein` and a `fadeout` in seconds: it fades in the first time it plays, and out before the end of the last. A sound with a fadeout fades out whenever it stops, cancelled or interrupted too, and a cancel with a fadeout of its own fades out everything it stops over that time. Hexad's `Sound` has `soundVolume`, `soundFadeIn`, and `soundFadeOut`, and `stopSoundLayer(layer, seconds)`.
- **The guide's page** has the button and the fades, in *The Gallery*: its bell is now a picture that lights up under the pointer and rings when clicked, and its fountain fades in and out.
- Checked in Chrome: a game with a pane at the left, a `<banner>` at the right, and the status line across the top; the same in a window 390 wide; and The Golden Skull as before.

**Done, 2026-11-27: the system's file dialog.**

- **A host can show a dialog of its own** for a file a program asks for (`inputFile`): `Host::choose_file`, with the program's prompt and whether the file is to be opened or saved, answers with the file, a cancel, or that the player has not chosen yet, on which the VM stops and asks again when it is resumed, as it does for a line. A host without one says so, and the VM asks for the name as a line after the prompt, as before: the terminal, `hexicon run`, the tests, and the page in a browser.
- **The WebAssembly build** shows it when the page says it can (`setFileDialogs`): the game then waits with `file`, `fileDialog()` says which dialog with what prompt, and `sendFileChoice(name)` answers, or cancels with nothing.
- **The player shows the system's own** (the `rfd` crate: Windows's, macOS's, and GTK's on Linux, which the web view needs already), with the prompt as its title, starting in the game's folder, in front of the window. A file chosen in the folder the game knows by its name there, as it knows the others. One chosen anywhere else it knows by the whole of its path, and the player writes it there, as the player chose; a path the player did not choose in a dialog, the player will not write. A file opened from elsewhere is read when it is chosen. A command script still gives a file's name as it always has, and no dialog is shown.
- **Saved games are `.hxs` files.** The program says what kind of file it asks for (`FileTypeSave`, `FileTypeLog`, ...), and the host is told (`FileKind`): the player's dialog shows saved games (`.hxs`) or text files (`.txt`), with all files a choice when opening one, and a file to save of that kind named without an extension is given it. A name typed as a line, in a terminal or a browser, is kept as it is.
- `HEXICON_CHECK_CHOOSE` answers the player's dialogs with a path, for checks: saved in the game's folder and restored from it, saved elsewhere and restored from there in a new run, and cancelled, all in WebView2. The dialog itself was not checked automatically.

**Begun, 2026-11-27: Linux** (Ubuntu under WSL, with WSLg).

- **The checks on Linux:** the tests, game-check, and doc-check were the same as on Windows from the first. program-check found 49 programs whose images differed, and only their images: an image records the files it was built from, and the preprocessor joined a built-in header's name to its folder with the system's separator, so Windows wrote `<hexicon>/systemector.h` where Linux wrote `<hexicon>/system/vector.h`. A built-in file is now named with `/` everywhere, as the manifest's were already, so an image is the same whatever it was built on; the 49 fingerprints, recorded on Windows, are recorded again, and program-check gives 535 the same on both.
- The build and check scripts take `CARGO_TARGET_DIR`, so a Linux build of the same folder keeps out of Windows's `target/`.
- **The player on Linux** needed its web view put in the window's GTK box, since a window shown by Wayland, as WSLg shows it, has no handle the web view can take. It plays sounds through GStreamer, which needs its plugins for the formats (`gstreamer1.0-plugins-good`, `-bad`, `-libav`) and for the sound server (`gstreamer1.0-pulseaudio`): without the last, as in a bare WSL, nothing is heard. A Linux package of the player should depend on them.
- **Spacing, found side by side:** a rich display showed more blank lines than a display of text, after a room's name and before the prompt. Two causes. The checker made every newline a line break, where the console adds nothing for a newline at the start of a line; it now does the same, but in `<pre>`. And Hexad's paragraph filter, which drops a paragraph break right after another, took the tags around its classes (`<span class="roomcontents">`, from step 5) for text in between; it now passes them through. A display of text gets what it always had; The Gallery's and The Golden Skull's rich transcripts lose only line breaks. The room's name has a little room under it in the page's defaults.
- **A short sound was never heard on Linux.** The page made an audio element each time a sound played, and WebKitGTK starts a GStreamer pipeline for each; under WSLg the start of the sound was lost with it, so The Gallery's chime, under a second long, was silent, while the fountain, which loops, played. The page now has an element for each of the game's sounds loaded when the game starts (`resourceNames()`), plays a sound from it, and makes the next one ready behind it. The bell rings on Linux as on Windows.
- **The command line went below a picture beside it.** It is a box of a fixed width, and where less room was left on the prompt's line beside a picture floated at the right, the box was put below the picture, away from its prompt. On a rich display it now takes the room its line has, allowing for the picture's margin, and is fitted again when a picture has loaded.
- **A room's sounds after RESTART, RESTORE, or UNDO.** Hexad kept the sounds it was playing as part of the game, so RESTART put it back to none playing, and it started the outside's sounds over the cave's, which went on. What is playing is the display's, not the game's: it is now kept in a transient object, so the next look at the player's room stops what is no longer the room's and plays what is. UNDO had the same fault.
- **Sounds play through Web Audio** (2026-11-27). The page had given each sound to a media element, which each system's own player plays (GStreamer on Linux, Media Foundation on Windows, AVFoundation on macOS), each starting, looping, and pausing in its own way: on Linux a short sound was lost and a loop had a gap, as the fixes above found one at a time. Now each of a game's sounds is decoded once, when the game starts, and the page says when its samples play: a loop is sample-accurate, a sound played a number of times is one run without breaks, and fades are on the audio's clock. So what a sound does is the page's code, the same on every system, and what is left to each is its decoder and its output. The browser's rule that a page makes no sound until the player has done something is one audio that waits, and plays what was started when the player first types or clicks. A decoded sound is kept whole, about 10 MB a minute in stereo, which a game with long music will feel. `window.hexiconSoundsPlaying()` says what is playing, and `web-check.js` prints it, so a check sees the sounds without hearing them; it starts the browser with sound allowed before anything is done.
