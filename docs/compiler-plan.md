# Hexicon Compiler Plan

Status: draft, 2026-11-19

## Goal

Build the Hexicon compiler in Rust: a program that turns source text into an image the Hexicon VM runs. The first target is compiling unmodified TADS 3 source, meaning a game's own files together with the library it is built on (adv3 or adv3Lite), into an image that plays the same as one built by the stock `t3make`.

The same compiler, built into the VM, is the dynamic compiler: the part that lets a running program compile code, which `DynamicFunc`, stack frame references, and `GrammarProd.addAlt` need. The ten conformance tests that still fail all wait for it.

Hexicon's own language comes after that, as changes to a compiler that already handles everything TADS 3 has.

## Scope

In scope:

- The preprocessor: comments, line splicing, strings that run over lines, `#include`, `#define` with arguments and variable arguments (`#foreach`, `#ifempty`, `#ifnempty`, `#argcount`), token pasting and stringizing, `#if` and its relatives, `#pragma`, `#line`, `#error`, `#charset`
- The tokenizer, including strings with embedded expressions (`<<...>>`) and their special forms (`<<if>>`, `<<one of>>`, `<<first time>>`, format specs)
- The parser for the whole language: expressions, statements, functions, objects and classes, `modify` and `replace`, templates, property sets, `grammar` rules, `dictionary`, `enum`, `intrinsic` and `intrinsic class`, `export`, anonymous functions and short-form anonymous functions, operator overloading
- Constant folding, as far as a program can tell that it happened
- Code generation to T3 byte code
- Symbol files and object files, or something that does their job: a library's sources are compiled separately and linked
- The linker and the image writer, including debug records
- Project files (`.t3m`) and library files (`.tl`)
- Preinitialization, which already exists: it is running the image in the VM and saving the result
- The dynamic compiler interface in the VM

Deferred:

- The JavaScript back end the reference has (`tcjs*`), which was never finished there
- Resource bundling (`t3res`), which is separate from compiling
- Hexicon's own language

## Principles

The VM plan's parity principle carries over. Where the reference compiler's behavior is deterministic and a program or its author can see it, Hexicon does the same thing, odd cases included. That covers what text a macro expands to, what a string with embedded expressions turns into, which errors and warnings are reported, and what the compiled program does.

It does not cover the bytes of the image. Two compilers can lay out an image differently and produce programs that behave identically, so image comparison is a tool, not a requirement. What is required is that the image runs the same.

The reference is the specification of record. Its source is in `../_tads/tads-runner/tads3` (`tc*.cpp`, `tc*.h`); the documents in `../_tads/tads-sources/t3doc` say what was intended.

## How each stage is checked

| Stage | Checked against |
|---|---|
| Preprocessor | The reference's preprocessed text (`test_tok -P`, `t3make -P`), line for line, over the suite's 12 preprocessor tests, every file of adv3 and adv3Lite, and the sources of the games in the playground that have them |
| Tokenizer | A listing of the tokens the reference's tokenizer finds (`tools/reference/tok_dump.cpp`), over the same files |
| Parser and code generation | The reference has nothing that shows a syntax tree, so the two are checked together: the same source compiled by both compilers, and the whole image compared byte for byte, along with the messages each compiler gives (`tools/compile-compare.sh`). The sources are hand-written programs for each feature (`tools/compile-tests`), a few hundred small ones that each probe one case or one mistake (`gen-cases.py` there), random programs made of whatever the compiler supports so far (`gen-random.py`), any of those cut off at a random place (`gen-truncated.py`), the same kinds of program as several source files (a folder of them, for the linker), projects with libraries and the system library, then the test suite's programs as the suite builds them (`suite-compare.sh`), then the games, each from its own project file (`game-compare.sh`), the images written after preinitialization against those of the reference's `t3pre` (`preinit-compare.sh`), and the conformance suite, then the games with walkthroughs. Programs that are meant not to compile have to give the reference's messages |
| Dynamic compiler | The ten conformance tests that need it |
| Whole | Airport (adv3Lite's tutorial game) and Return to Ditch Day built from source by Hexicon alone, replayed against the reference build |

## Milestones

1. **Preprocessor.** Text in, preprocessed text out, identical to the reference's.
2. **Tokenizer.** The stream of tokens the parser reads, identical to the reference's.
3. **Functions: parser and code generator together.** Expressions and statements, parsed, folded, and compiled to byte code, with enough of an image writer to make a single-file program of functions runnable. Checked by compiling the same source with both compilers and comparing the byte code and the output. This is also what the dynamic compiler needs. Exit: the ten remaining conformance tests pass.
4. **Objects, grammar, and the rest of the language.** Enough to compile any single-file program to an image. Exit: the conformance suite's programs, compiled by Hexicon, give the same output as when compiled by `t3make`.
5. **Separate compilation, linking, project files.** Exit: the sample game, Airport, and Return to Ditch Day built from source and replayed identically.
6. **Hexicon's own language.** Its file extensions and its differences from TADS 3 are decided here, not before. The compiler accepts `.t`, `.h`, `.tl`, and `.t3m` throughout.

## Workspace

```
crates/
  hexicon-compiler/       the compiler as a library: no file system or console of its own
    src/pp.rs             the preprocessor
    src/lex.rs            the scanner that finds the next token on a line
    src/tok.rs            the tokenizer: the stream of tokens the parser reads
    src/parse.rs          the parser: tokens to a syntax tree and the program's symbols
    src/ast.rs            the syntax tree
    src/fold.rs           working out constant expressions
    src/flow.rs           how control leaves a statement: what can and cannot be reached
    src/emit.rs           the code generator: the syntax tree to byte code
    src/codegen.rs        the code stream and the instruction writer, with its peephole rules
    src/project.rs        what to build: the options and the modules, from the command line,
                          project files (.t3m), and libraries (.tl), as t3make reads them
    src/link.rs           putting the source files of a program together: the numbers that
                          objects, properties, and enumerations have in the image
    src/image.rs          the image writer: pool layout, addresses, and the image's blocks
    src/compile.rs        the two readings of each source, and what comes back to the caller
    src/ppexpr.rs         constant expressions for #if, until the parser takes them over
  hexicon-cli/            `hexicon build`, `hexicon preprocess`, and `hexicon tokens`
tools/
  pp-compare.sh           preprocesses files with Hexicon and the reference's test program, and compares;
                          with --tokens, compares the tokens
  reference/tok_dump.cpp  lists a file's tokens using the reference's own tokenizer
  compile-compare.sh      compiles files with Hexicon and with `t3make`, and compares the images
                          and the messages; a folder is a program of several source files
  image-diff.py           compares two images, leaving out the parts that mean nothing
  compile-tests/          programs for compile-compare.sh, and the generator of random ones;
                          suite-compare.sh builds the test suite's programs with both compilers,
                          and game-compare.sh the games, each from its project file
```

The compiler reads files through a small interface the caller supplies, as the VM reaches the outside through its host. That keeps it usable inside the VM, in a browser, and in tests.

## Status

- Milestone 1: the preprocessor is written and matches the reference (2026-11-19). `hexicon preprocess` writes a file's preprocessed text in the form the reference's preprocess-only mode does. Over 579 source files, about three million lines of output, it is identical to the reference's, messages included: the suite's 12 preprocessor tests and 381 test programs, every file of adv3 and its extensions, Return to Ditch Day, every file of adv3Lite, and Airport. Still to do in this milestone: `#if` expressions through the real expression parser.

- Milestone 2: done (2026-11-19). `hexicon tokens` lists a file's tokens as the compiler proper reads them: after preprocessing, with keywords recognized and strings translated. Over the same 579 files, it lists the same tokens as the reference, with the same messages.
- Milestone 3: under way. `hexicon build` compiles a single-file program of functions and objects to an image, and the program runs: it can call the virtual machine's built-in functions, so it can print (2026-11-19). It has `intrinsic` declarations of built-in function sets; parameters (plain, `...`, `[rest]`, optional as `count?` or `count = 1`, and passed by name as `count:`); locals and nested scopes; `if`, `while`, `do`, `for` (with `in` over a collection or a range), `foreach`, `switch`, `break` and `continue` with and without labels, labels and `goto`, `try` with `catch` and `finally`, `throw`, and `return`; and expressions over integers, strings, lists, objects, `nil`, `true`, locals, anonymous functions (`{x: x + 1}`, `function(x) { ... }`, `method(x) { ... }`) that share the locals and the `self` of the code they are in, and calls to functions by name or through a value, with arguments passed by position or by name (`f(1, count: 3)`), with indexing, assignment to an element, strings in double quotes that are displayed, and every operator except those listed below as still to do, `is in` and `not in` included. Strings of both kinds can have expressions embedded in them (`<<...>>`), with `<<if>>` and `<<unless>>`, a format (`<<%d x>>`), and string templates (`string template`). Objects and classes are defined with their superclasses, properties, and methods, with or without a name and with or without braces, starting if they like with values that a template gives properties to (`object template 'name' "desc"?;`, `Thing template ...;`). An object can be put inside the one before it with `+` signs (`+ property location;`), a property's value can be an object written in place (`prop: Thing { ... }`), properties can be grouped under a pattern for their names (`propertyset 'verify*' { ... }`), and a property's value can be worked out once before the program starts (`prop = static expr`); code can use `self`, get and set properties (`obj.prop`, `obj.(expr)`, and in a method the property's name alone), call methods, call what a method overrides (`inherited`), make objects (`new`), take the address of a property (`&prop`), and ask about the method that is running (`targetprop`, `targetobj`, `definingobj`, `invokee`). A method can run another object's method as its own (`delegated`) or stand for an operator (`operator +(other) { ... }`), and any function can ask how many arguments it was called with (`argcount`). An object can be written in an expression (`object: Thing { ... }`), to be made when the expression is evaluated, and `defined(name)` and `__objref(name)` ask about a name when the program is compiled. The classes built into the virtual machine are declared with `intrinsic class`, which makes their methods available (`list.length()`, `new Vector(10)`), and a program can include the system's own header files for them; A second definition can take the place of a function or an object (`replace`) or go in front of it (`modify`, with `replaced` for the function as it was and `replace` before a property to take the old one away), and `modify` can add to the classes built into the virtual machine. `extern` declares a function, an object or a class ahead of its definition, and `transient` marks an object as not to be saved. A number can have a point or an exponent (`1.5`, `2e10`), an integer too large to be one becomes such a number, and `R'...'` is a regular expression; the compiler makes each an object, and does arithmetic on constant numbers itself. `property` declares property names, `enum` declares the values of an enumeration, and `export` makes names known to the virtual machine. `<<one of>>` and `<<first time>>` in a string choose among alternatives, with an object of the class `OneOfIndexGen`, which the program has to define, as the system library does. A list of `key -> value` pairs is a lookup table. `dictionary name;` makes a dictionary, and `dictionary property noun;` a property whose value is words for it (`noun = 'lamp' 'lantern'`); the compiler puts each object's words, and its classes', in the dictionary. `grammar name(tag): tokens : Class ...;` says how a phrase can be made up and defines the class of the object made when one is matched. Over 28 hand-written programs, 469 small ones that each probe one case or one mistake, and 8,700 random programs, it writes the same image as `t3make`, byte for byte, and gives the same messages. The exceptions, about one random program in a hundred, are a constant divided by zero and `nil` added to a constant string, where the reference's result depends on what is in its memory (see the findings). Hexicon gives a different answer on purpose in two places, the right one each time: a constant division of numbers that are not both integers, and the words of a program with more than one dictionary (see the findings). A program that modifies one function twice in one source file is one the reference cannot put together at all, and a method in a `propertyset` that has parameters stops the reference with a memory fault (see the findings); Hexicon compiles both. A pointer can be taken to a built-in function (`&tadsSay`), `rand()` with two or more arguments evaluates only the one it chooses, as the reference compiles it, a method can be defined at the outermost level (`method name() { ... }`), for an object to take with `setMethod`, and `#pragma sourceTextGroup` gives each object the object that stands for its source file. The compiler's predefined macros are in (`__TADS3`, the version numbers, `__DATE__`, `__TIME__`, and the system's name, which for Hexicon is `HEXICON`). Anything else in the language is reported as not supported yet. Functions can be chosen by the kinds of their arguments (`put(Thing a, Box b) { ... }`, a version of the multi-method `put`), with the system library doing the choosing. That is the whole language. Still to do in this milestone: the dynamic compiler itself.

- Milestone 5: under way (2026-11-21). `hexicon build` takes what the reference's `t3make` takes: source files and libraries on the command line or in a project file (`-f game.t3m`, or `makefile.t3m` if nothing is given), with the reference's options for macros, folders, warnings, and preinitialization; it starts the build with the system library's `_main` unless told not to (`-nodef`, or `nodef` in a library), and looks for libraries and sources where the reference does (`-Fs`, `TADSLIB`, and the system library, `-FL`, which is `lib` beside the program unless said otherwise). Each file is read once to learn what it defines, then again, knowing what all of them define, to generate its code; and then what was generated for each is made into one program, with objects, properties, and the values of enumerations given the numbers the reference's linker would give them. A file can use the functions, objects, classes, properties, and enumerations of any other; the files share dictionaries and grammar productions, each adding its words and rules; each can add to the classes built into the virtual machine; multi-methods can have versions in several files; and a file can `replace` or `modify` a function, an object, or a grammar rule that an earlier file defines. What two files both define, and what none defines, is reported as the reference reports it, and so is what is wrong with a library or a project. The two games are built from their own project files, Airport on adv3Lite (55 modules) and Return to Ditch Day on adv3, and the images are the same as `t3make`'s, byte for byte, with no messages from either; so are those of all 126 programs the test suite builds with `t3make`, built as the suite builds them, and of 11 small projects that each probe one case of libraries and project files. Return to Ditch Day, built by Hexicon, plays under Hexicon's VM as the reference's build does. All of that is without preinitialization (`-nopre`). With it, as the project files ask, `hexicon build` runs the program once before writing the image, as `t3make` does: the program can ask for the tables of its global symbols and its macros, which have the same entries in the same order as the reference's, and the image written is what the run leaves, with the strings and lists it made turned into constants. Return to Ditch Day built that way plays its walkthrough to a win, 7,106 lines, the same as the reference's build, and Airport plays as the reference's build does. `hexicon preinit` does to an image what the reference's `t3pre` does, and over 120 images (the 118 of the suite's programs, and the two games), the images it writes are the same as `t3pre`'s for 118; the other two are a program that reads keys at the end of input, where the two consoles differ, and Return to Ditch Day. That game, and Airport from `hexicon build`, differ from the reference's builds only in the numbers of the objects the run made, because the reference's collector runs at times Hexicon's does not yet match (see the findings). Airport's image also has Hexicon's system name in its table of macros. Over a hand-written program of four files that runs, 35 small programs of two or three files that each probe one case, and 226 random programs of two to four files that the reference compiles, the image is the same as `t3make`'s, byte for byte, but for two random programs: one with `nil` added to a constant string, and one with an object that has the same property twice (see the findings). Every program of one file goes the same way, as a program of one. Still to do in this milestone: collecting garbage at the reference's times while preinitialization runs, so that the objects it makes get the reference's numbers; and resources (`-res`, and `resource:` in a library), which are reported as not supported yet.

## Findings

From milestone 1:

- The preprocessor is a port of the reference's, routine for routine, and not a design of its own, because what it has to reproduce is the exact text a macro expands to, and that comes out of the order the reference does things in. A macro's stored expansion has marker bytes for its parameters; expanded text carries markers that say which macro each part came from, which is how a macro is kept from expanding inside its own expansion.
- A line is one line of output for each line of source, so that line numbers still mean something afterward. A string that runs over several lines is joined into one, and whatever follows the string on its last line becomes a line of its own.
- The reference keeps a line as text that ends at a zero byte together with a separate count of its length, and a `//` comment ends the text without changing the count. Text spliced on afterward goes after the count, where nothing that reads up to the zero sees it. The effect a programmer can see: in a macro call that runs over lines, a `//` comment loses the rest of the argument it is in. `PAIR(one, // note` followed by `two)` gives the macro an empty second argument. Hexicon keeps its line the same way and does the same.
- The stack that `#foreach`, `#ifempty`, and `#ifnempty` nest on is static in the reference, shared by every expansion in progress. Expanding a macro inside an argument of another starts it over. Hexicon shares it too.
- A file named in an `#include` with quotes is looked for only beside the file that includes it, then on the include path. The reference has a loop that looks like a search up through the files that led to this one, but every pass of it looks in the same folder.
- `#pragma newline_spacing`, `#pragma sourceTextGroup`, `#pragma message`, and `#error` are for the compiler proper. When only preprocessing, they are passed through, with macros expanded in the last two.
- A source file's character set is found when it is opened: a byte order mark, or `#charset "name"` as the very first thing in the file, with exactly one space after `#charset`. Without either, it is ASCII, and a byte that is not ASCII becomes U+FFFD. A `#charset` naming a set that is not known is left in the text, where the preprocessor reports that it could not be loaded.
- The messages are the reference's short forms, word for word, and are reported at the same lines. An `#if` left open at the end of a file is reported against the line after the last one.
- An `#if` condition that cannot be evaluated counts as true, as in the reference.
- The reference's test program (`test_tok -P`) is the oracle, and it differs from the compiler proper in three ways that the comparison inherits: it defines a handful of macros of its own (`_WIN32` and the like) and not the compiler's (`__TADS3`, `__DEBUG`, and so on); it names files without their folders; and it cannot load the character set tables, so files in `cp1252` or `win1251` are compared as files whose character set failed to load.

From milestone 2, so far:

- The reference has no program that lists tokens: its tokenizer test only writes lines. `tools/reference/tok_dump.cpp` is a driver of Hexicon's own, built against the reference's sources by the same build that builds its test programs, and `pp-compare.sh --tokens` compares against it. The kinds of token are numbered here as they are there, so the listings can be compared as text.
- A string's token carries the translated text: escape sequences are replaced by the characters they stand for. A string with embedded expressions is several tokens: the text up to the first `<<`, the tokens of the expression, the text after `>>`, and so on. A format (`<<%2d n>>`) is a token of its own after the text before it. Whether `>>` ends an embedded expression or is a shift depends on whether any brackets are open inside the expression.
- What comes after `<<`, such as `if`, `one of`, and `first time`, is ordinary tokens at this stage. Making sense of them is the parser's job.
- After a character that is not valid, the reference skips the character after it as well. So does Hexicon.
- A `#pragma message` is shown as the file is read, and `#error` is reported as an error with the rest of its line, the space after `#error` included.

- The compiler knows ASCII, UTF-8, UTF-16, and Latin-1 itself, and asks whoever is using it for any other character set a source file names. The command-line program answers from the VM's tables, which are the reference's, so a source file can be in any of the sets a program can use. This closed a gap that was hidden at first: the reference's test programs could not find their character set tables, so files in `cp1252` and `win1251` were being compared as files whose character set failed to load. The reference build now puts the tables where the test programs look (`bin/charmap`), and those files are compared decoded.
- How the parser can be checked, which decides the order of the work from here. The reference has no way to show a syntax tree. Its expression test program (`test_prs`, now part of the reference build) shows what an expression folds to and the code it compiles to, but it has not kept up with the compiler: it crashes on an expression that uses a local variable, so it is only good for constants. What does work is `test_prs_top -u`, which compiles a whole single-file program, writes a runnable image, and lists the code. So the check on the parser is the code that comes out the far end: the same program compiled by both, with the byte code compared function by function and the two images run. The parser and the code generator are therefore built together, a part of the language at a time, and not one after the other.

From milestone 3, so far:

- The check is `t3make -nodef -nopre` on a single file against Hexicon's image, the whole file compared. Some of the reference's image cannot be reproduced and is left out of the comparison: the time stamp; the four bytes of the build configuration in the header; two bytes of padding after each exported symbol's value in the `SYMD` block, which the reference never sets; and, in a function's table of locals, the field for a local's place in a shared context, which the reference never sets for a local that is not shared and which then holds whatever its memory did. Hexicon writes zeros in the last two. Rather than have the comparison know the image's layout, `hexicon build --unspecified` lists these stretches of its own image, and the comparison skips them in both.
- The reference reads a source file twice: once only to learn what it defines (the symbol file `t3make` writes), and again, knowing that, to generate code. Hexicon does the same, because it shows: a function can be called before the line that defines it, and some messages come only from one reading. A `while` whose condition is always false is warned about on the first reading and not the second; an `if` on the second and not the first. The reference's messages from the first reading come out before those of the second, and so do Hexicon's.
- Constants are folded twice as well. Each operator is folded as it is parsed, when both operands are already constants. After the whole program has been read, names are looked up, and a name that is a function becomes a constant; then only the comma, `+`, `-`, `==`, `!=`, `&&`, `||`, `!`, `?:`, and `??` are tried again.
- Once a function's name has become a constant, a call through it is taken to leave a value whether or not the function returns one. That matters in `a ? f() : g()`, where a branch that leaves no value has `nil` pushed for it: after folding, no call by name is such a branch.
- A statement's code depends on small things that are easy to get wrong and that the comparison found: `x * 0` evaluates `x` and pushes zero even when the value is not wanted, leaving it on the stack; an integer from -128 to 126 is pushed in two bytes, but 127 takes five; a jump to the very next instruction is taken back out when the label is placed; and nothing is written after an instruction that cannot be fallen out of until a label is placed.
- A local declared as the single statement of an `if` or a loop, with no braces, belongs to the scope around. `if (a) local b = 1;` declares `b` for the rest of the enclosing block. A `for` has a scope of its own for the locals in its parentheses, and a braceless body's locals go there.
- Each scope that declares locals takes new slots for them, and slots are never used again by a later scope, though the reference has a comment wishing they were.
- Warnings about locals that are never used, or never given a value, come after all the code has been generated, function by function and scope by scope, in the order of the reference's hash table, and are reported at the line of the declaration. An unused parameter is not warned about by default.
- Two places where the reference's result depends on what happens to be in its memory, and Hexicon's does not. Adding `nil` to a constant string (`'ab' + nil`) reads past the end of an empty string in the reference; in Hexicon it adds nothing. A constant division by zero is reported once by Hexicon; the reference goes on to use a flag it never set, and usually reports it twice.
- In the reference built for Windows, a constant multiplication that overflows 32 bits wraps around, because its arithmetic there is 32 bits wide before it looks for the overflow; built elsewhere it becomes a floating-point number. Hexicon wraps, as the reference it is compared with does.
- `name { ... }` is not a function without parameters; without the keyword `function` it is taken for an object.
- A name in a message is cut to 60 bytes, with `...` after it, by the reference's message formatter. Hexicon does the same for every name it shows.
- A symbol longer than 80 characters draws a warning that it has been truncated, but the tokenizer passes it on whole. A local with such a name gets a broken entry in its function's table: the reference collects the names of locals in a stream of their own before moving them to the constant pool, does not move one longer than 80, and leaves the table holding the name's offset in that stream as if it were an address in the pool. It is the same number every time, so Hexicon writes it too.
- A source file that does not say what character set it is in (no byte order mark, no `#charset`) is read by `t3make` in the system's own character set, which on the Windows machine the reference was built on is code page 1252; the reference's tokenizer test program reads it as ASCII. Hexicon reads it as UTF-8, which is what a new source file is most likely to be in and does not depend on the machine; `-cs name` says otherwise. The comparisons pass `-cs cp1252` or `-cs us-ascii` to match the program they compare with.
- A built-in function is known by the number of its set and its number in the set, in the order the `intrinsic` declarations give them. Built-in functions are not in what the first reading of the source hands to the second: each reading declares them as it comes to them. A name of a built-in function without parentheses is a call with no arguments.
- A set of built-in functions declared twice keeps the later version, but by overwriting: the reference compares as many bytes as the new version has, and if the new is greater, writes them over the start of the old. `'seven/123456789'` and then `'seven/2'` leave `seven/223456789`. Hexicon does the same. A set declared first without a version and then with one gets, in the reference, whatever followed the name in its memory; in Hexicon it gets the version.
- Calling a built-in function numbered above 255 in its set crashes the reference compiler. Hexicon generates the long form of the instruction.
- A constant list is a count and five bytes for each element; the strings and lists among its elements follow it in the pool, and the elements hold their addresses. Lists are not shared the way short strings are. The longest list in the source, constant or not, counts toward the size of the pool's pages. For an element that is `nil` or `true`, only the first of the five bytes means anything, and the comparison skips the rest.
- The reference folds `==`, `!=`, `!`, `&&`, and `||` by overwriting the left operand's value in place, and when that operand is a constant list, what is left is a list that claims to be `true` or `nil`. Whatever asks for its value sees the truth value: `return [1] == [1];` returns true, and `if ([1] == [2])` is a condition that is always false. But where code is generated for it as an expression, the list is pushed: `local a = [1] == [1];` sets `a` to `[1]`. It is the same every time, so Hexicon does it too.
- Assigning to an element (`a[i] = v`) is three steps: the value, then the container and the index, then `setind`, which gives a new container; and then that is stored back into `a` if `a` can be assigned to, or discarded. The instruction writer turns the common case, a local indexed by a small constant, into one instruction.
- A string in double quotes is displayed where it stands (`say`), and using it for its value is an error. In `a ? "x" : f()` it counts as a branch with no value.
- The reference stops after working out constants if that found anything wrong, before generating any code. So a program with a `case` that is not a constant, or a constant index out of range, gets none of the messages that generating code would give (an undefined name, a local never used).
- A `switch` is the value, then one instruction holding a table: the number of cases, a kind and four bytes and a jump for each, and a jump for when nothing matches. The table is written empty, and each `case` and the `default` fills in its own entry when its code is come to. Each jump is measured from where it is written. A case that is `nil` or `true` has four bytes that mean nothing, as in a constant list. The number of cases is counted by the parser, and the count includes a `case` that the parser then drops for coming before anything reachable.
- The end of a `switch` is given a place to jump to only if working out the control flow says that what follows can be reached. If it cannot, a `break` in the switch generates nothing.
- A `case` or `default` has to be followed by a statement: `default: }` is a syntax error.
- A function's labels are in a table of their own, of the size of the table of global names (512 chains, where a scope's locals have 32), and the warnings about labels that nothing refers to come in that table's order, after the function's code is generated.
- A use of a label is recorded when the parser works out a function's control flow, so a `goto` in code that cannot be reached does not count, and its label is reported as not referenced.
- The code generator works out control flow again for each `switch` and each `finally` block. A `goto`, `break`, or `continue` naming a label that it meets then is recorded as a use of the label of that name in the last function of the source file, whatever function the statement is in, because the parser is still holding that function's table. So a label in the last function that nothing refers to gets no warning if another function has a `switch` with a `goto` to a label of the same name. Hexicon does the same.
- A statement whose label's name was already taken has no label as far as the reference is concerned, and looking up a name the function does not have also finds no label, so the two match: `break nosuch;` inside such a statement leaves it, with no complaint beyond the one about the name. Hexicon does the same.
- `continue` can name a label only if the label is directly on a loop (or on another label that is).
- A `finally` block is a subroutine within the function. Leaving the protected code any way at all calls it first (`ljsr`): falling out of the end, `break`, `continue`, `goto`, and `return`; and so does the handler for an exception, which keeps the exception in a local, calls the block, and throws the exception again. The block starts by putting where to go back to in a local, and ends with `lret`. The two locals come after the function's own: where to go back to, and then the exception. A `return` with a value keeps the value in one more local while the blocks run; that local is added when the code is generated, one for the whole function.
- A function with a `try` has a table of exception handlers between its code and its table of local names: a count, and ten bytes for each (the first and last byte of the protected code, the class caught or zero for all, and where the handler is).
- If a `finally` block cannot be fallen out of (it returns or throws), no jump past it is generated after the call.
- The parser takes a `catch` block to be outside its `try`, and the code generator takes it to be inside. A `goto` from a `catch` block to a label in the same block therefore counts as leaving the `try`, and calls the `finally` block before jumping.
- `goto` cannot jump into a `finally` block. It can jump into anything else, a loop or a `try` included.
- `goto` with no label after it crashes the reference compiler, which goes to write a message that names a token without having been given one. Hexicon reports the token it found.
- A string with expressions embedded in it comes from the tokenizer in pieces, and the parser puts them together. In double quotes, `"one <<two>> three"` is `"one ", say(two), " three"`: each piece of text is displayed, and each expression is worked out and what it leaves is displayed (`sayval`). An expression that leaves nothing, a call to a function that returns no value, is worked out for what it does. In single quotes, `'one <<two>> three'` is `'one ' + (two) + ' three'`. The additions are not worked out when they are parsed but with the other constants afterward, so a string with only constants embedded is a constant, and can be a `case`.
- An empty piece of text is left out, but for the first piece of a string in single quotes, which makes what follows a string whatever is added to it.
- The parser reads all the tokens of an embedded expression, up to the next piece of the string, before it decides what they are. So a mistake in an embedded expression that runs over several lines is reported on the line where the next piece of the string ends.
- `<<if x>>`, `<<unless x>>`, `<<else if x>>`, `<<else unless x>>`, `<<else>>`, and `<<end>>` make the conditional operator of what is between them; `otherwise` can be written for `else`. `<<end>>` can be left out: the end of the string, or the end of whatever the `if` is inside of, ends it. Without an `else`, the other branch is an empty string. `else` is taken for the end of an `if` wherever it is, and is an error if there is none. The other words (`end`, `otherwise`, `or`, `only`, and the phrases that end `<<one of>>`) mean something only inside their construct; anywhere else they are ordinary names in an expression.
- The words of these constructs are matched as text, whatever kind of token has it. `<<'or'>>`, a string, is taken for `<<or>>`. The exception is `else`, which has to be the keyword once it has been recognized: `<<'else'>>` ends the branch it is in and is then an error.
- `<<%d x>>`, an expression after a format, is `sprintf('%d', x)`. The function is found by its name among the program's global names, so the program has to declare the built-in function, and a local variable called `sprintf` makes no difference.
- `<<one of>>` and `<<first time>>` keep their state in an object of the class `OneOfIndexGen`, which the program has to define; without it they are read and then reported as needing the class (see the finding on the object further down).
- `string template <<tokens>> function;` makes an embedded expression of those tokens a call to the function. `*` among the tokens stands for one or more tokens, which are the function's argument; what they are is looked for among the templates in turn, so templates nest. The templates are tried in the order they were defined, and the first that fits is used. Tokens are compared as text.
- A template's function need not be defined yet. If it is not, the template declares it, as taking one argument if there is a `*` and none if not, and a definition that follows has to agree. If it is defined already, it has to take that many arguments and return a value. A function that was declared by a template first and defined afterward is not checked for returning a value.
- A function that is declared and never defined is an error only if something refers to it: `unresolved external reference`, with no place in the source, after everything is generated. Several are reported in the order of the table of global names.
- The compiler gives up after a hundred errors: the hundred-and-first is followed by `fatal error: too many errors`, at the place being read or generated, and nothing after that. This holds while reading the source, working out constants, and generating code. It is what ends the reference's attempts to finish a string that the source ends in the middle of, which would otherwise never end.
- A name that nothing defines is reported once. The reference then notes the name as known to be undefined, and later uses of it, in whatever function, generate nothing and say nothing.
- A string token named in a message is cut to twenty characters, with `...` if there was more, and its control characters are written as escapes (`\n`). For a control character without an escape of its own the reference means to give the code in hexadecimal, but adds the character `0` to each digit, which gives letters and backquotes. Hexicon does the same.
- Three things about strings that the reference crashes or hangs on. An empty embedding with text after it, when nothing comes before the two in a string in double quotes or in a branch of an `<<if>>` there (`"<<>>text"`), leaves a hole in the syntax tree, and the reference crashes on it; Hexicon displays the text. `string template <<` with no `>>` before the end of the source never stops reading; Hexicon reports the missing `>>`. And a template whose function's name is a built-in function's is taken to be a function of the program's own, reading what is not there; Hexicon reports that the function does not match the template.
- An object definition is a name, a colon, the superclasses (or `object` for none), and the properties, up to a semicolon; or the properties can be in braces, where semicolons between them mean nothing. `class` before it makes it a class. Without the name and the colon, it is an object with no name: at the outermost level, a name that is already an object's and is not followed by a colon or a parenthesis starts one, and so does `object`. On the first reading of the source, when not everything is defined yet, any name not yet defined is taken that way.
- A property is `name = value`, or a method: `name(parameters) { }` or `name { }`. A value that is a constant goes into the object as it is, and so does a string in double quotes, as text to display. Any other value becomes a method that returns it, or that only works it out if it has no value. This is decided after constants are worked out, so `size = 2 + 3` is the constant 5.
- An object that is not a class is given the property `sourceTextOrder`, numbered from 1 in the order the objects come in the source. The source can give the property a value of its own; any other property defined twice in an object is an error.
- An object with more than one superclass and no constructor is given one, which passes whatever arguments it gets to each superclass's constructor in turn. A constructor returns the object, whatever it says: falling out of it or `return` gives `self`, and `return` with a value is an error.
- In the image, the objects are in one block, in the order the source defines them. Each is its number, its size, the count of superclasses, the count of properties, a flag for a class, the superclasses' numbers, and the properties in order of number, each a number, a kind, and four bytes. The reference means to start a new block every 64,000 bytes, but never adds up what it has written, so there is only ever one. Where a property is `nil` or `true`, the four bytes are whatever was in the reference's memory.
- Properties and objects do not have their final numbers while the program is compiled. The reference numbers them when it links, in the order it reads the names from the object file, which is the order of the compiler's table of global names at the end: chain by chain (a name's chain is the sum of its bytes modulo 512), and in a chain the names first met on the second reading of the source, newest first, then those from the first reading, oldest first. Objects with no name are numbered after the named ones, in the order of the source. The 25 properties every program has (`construct`, `finalize`, `sourceTextOrder`, the operators, and so on) keep the numbers 1 to 25. So Hexicon generates code with provisional property numbers, notes where they are, and replaces them at the end.
- A name that nothing defines, used in a method or in a property's value, is taken to be a property, with a warning (`assuming this is a property name`). So is the name after a `.` anywhere. In a function, where there is no `self`, a name alone that nothing defines is an error.
- The name after a `.` is looked up among the global names only, never the locals. In parentheses it is an ordinary expression, whose value says which property. The name is resolved like any other first, so the name of a function or an object there is that function or object, and is reported as not a property.
- What is generated for `x.prop` depends on what `x` is: `self`, an object named in the source, a local, or anything else each has its own instruction, and so does a call with arguments. With `x.(expr)` the property is worked out and the call goes through a pointer. Assignment is the same again, and an assignment that changes a value in place (`+=`, `++`) gets the value and sets it without working out the object twice.
- A constant list is still a list to the reference's code generator, not a constant, so a list on either side of a `.` is generated as an expression where another constant would be an error.
- Adding to an object or subtracting from it is not worked out when compiling, even if the other side is a constant: the object's class may define the operator. Two objects are equal if they are the same object, and that is worked out.
- A method of the built-in classes, such as a list's `length()`, is a property that the class has to be declared with (`intrinsic class`), which is still to do. Until then such a name is an ordinary property, and the list has no such property when the program runs.
- An object definition whose end was left out is noticed when a property's name turns out to be followed by a colon. If the name is an object's, the definition ends there, and the rest is read as the next definition. If it is not, what follows is taken to be an object written in place as the property's value, which needs braces; without them the definition is reported as not ended, and reading goes on for one more property before it stops.
- A jump out of a `try` calls the `finally` block, but the reference decides what a jump is inside of from two different records. The code generator keeps track of the statement it is generating, and counts a `catch` block as part of its `try`; each statement also remembers what the parser took it to be inside of, and the parser takes a `catch` block to be outside its `try`. A jump starts from the first and carries on outward by the second. So `return`, `break`, `continue`, or `goto` straight out of a `catch` block calls the `finally` block, and the same jump from inside a loop, a `switch`, or a labeled statement in the `catch` block does not. Hexicon does the same.
- A `goto` to a label in code that was left out as unreachable (the `else` of an `if` whose condition is always true, say) is a jump to nowhere. The reference finds it when it has finished the function, and reports `internal error: 1 unresolved branches`, with the count of such jumps and no place in the source; the program is not compiled. Hexicon used to write the image with the jump going nowhere, and now reports the same.
- `inherited` is always the left side of a member expression: `inherited.prop(args)`, or `inherited(args)`, where the property is the one being run (`targetprop`) and the call goes through a pointer. `inherited Class` names the superclass to look in. All of these need a `self`.
- `new Class(args)` pushes the arguments and the class and makes an object of the first metaclass, with the class as one more argument. Only an object named in the source can be made this way for now; anything else after `new` is an error.
- `&name` is the address of a property, a constant. If the name is nothing yet when the `&` is read, it becomes a property, but a weak one: a function defined with the name afterward takes the name over, and it is then the function's address. An object defined with the name afterward is an error. Only a name can follow `&`; a local variable's name there is taken for a property's.
- Two addresses compared (`&a == &b`) are worked out when they are parsed, by comparing the names, before it is known what the names stand for.
- A property's number in a list, an object, or a `switch` takes two bytes of the four a value has room for; the other two are whatever was in the reference's memory.
- The constructor the compiler makes for an object with several superclasses is given the table of labels the parser was last using, which is that of the last function or method in the source. So a label there that nothing refers to is reported once for that function and once more for each such object. Hexicon does the same.
- `intrinsic class Name 'vm-name/version': Superclass { ... }` gives the program's name for a class built into the virtual machine, and lists the class's properties in the virtual machine's own order, which is how the two agree on which is which. Parameter lists there are read and forgotten. The image's table of built-in classes starts with eight every image has, in a fixed order; a declaration of one of those only raises its version, and a class that is new to the table is added at the end, in the order of the declarations. The class of the objects that stand for classes (`intrinsic-class`) is added last of all when the image is written, unless the program has declared it. Each entry has the numbers of the class's properties.
- A declared class has an object standing for it, which is what the class's name is in an expression. These objects are in a block of their own after the program's objects, in the order of the table of classes, and are numbered along with the program's objects, by the names.
- A property is numbered when its name is come to in the table of global names, or when the name of a built-in class that declares it is come to, whichever is first; a class's properties are then numbered in the order the class declares them.
- A built-in class's name is no object as far as most of the compiler goes: it cannot be a superclass, be caught, be assigned to, or be called. It can be the left side of a `.`, an operand of `new`, and a value.
- `property a, b;` makes the names properties. `export name 'external';` puts a name in the image's list of what the virtual machine can look up, under the external name, or under its own without one; the name can be a property's, an object's, or a function's. Exports are listed in the image before the names every image has, in the order of the statements. They are worked out when the image is written, so what is wrong with them (a name nothing defines, which is taken for a property with a warning; an external name used twice, or reserved) is reported last and with no place in the source.
- `static` in an `intrinsic class` list with no property name after it crashes the reference compiler, which goes to write a message that names a token without having been given one. Hexicon reports the token it found.
- After `export name 'external'` the reference checks for the semicolon but leaves it to be read as an empty statement.
- `foreach (x in coll)` and `for (x in coll)` get an iterator from the collection, keep it in a local the source has no name for, and at the top of each turn take the next value from it or leave the loop (`iternext`). What gets the iterator is the first property the program declares the built-in class `collection` to have, so without `intrinsic class Collection` neither loop compiles. The variable can be any expression that can be assigned to, or `local x`.
- `for (x in from..to step by)` counts. The variable is given the first value among the initializers; the end and the step are worked out once there and kept in locals of their own unless they are constants. At the top of each turn the variable is compared with the end, the right way round if the step is a constant integer, and both ways round by the step's sign if not. An `in` clause is one of the `for`'s initializers and can stand among others, and there can be several; with one, the condition and the rest can be left out altogether.
- A `for` with an `in` clause, and any `foreach`, is taken to finish, whatever is in it.
- `x is in (a, b)` and `x not in (a, b)` compare the left side with each value in turn and stop at the first that is equal. The reference means to work the test out when compiling if the left side and some of the values are constants, but looks at the wrong thing to tell whether a value is a constant and never finds one; so only a test against an empty list, with a constant on the left, is worked out. Hexicon does the same.
- Where the reference's parser can go round for ever at the end of the source, reporting an error each time, the limit on errors is what stops it. One such place is a `for` whose header the source ends in. Hexicon's limit did not get it out of that loop, and it hung; it does now. Programs cut off at 700 random places were then compiled with both compilers to look for more such places: there were none, and the messages were the same but for differences already known.
- `goto` with nothing after it but the end of the source does not crash the reference as `goto;` does: the message names the token as nothing.
- A program with no `_main` is reported before its exports are looked at.
- An anonymous function is `{params: expression}`, `function(params) { ... }` or `method(params) { ... }`, with `new` in front of the last two if the source likes. Its code is a function like any other, generated after everything else in the program, in the order the functions were finished, so one nested in another comes first. Where it is written, the code makes its value: the address of the code alone if the function shares nothing, and otherwise an object of the built-in class `anon-func-ptr` made of the address and the contexts the function needs.
- A local that a nested function uses does not live on the stack. The function it belongs to makes a vector on entry, its context, kept in a local the source has no name for, and every use of the shared local anywhere in the function, before the nested function or after, is an element of that vector (`idxlcl1int8`, `setindlcl1i8`). The local keeps its place on the stack, unused. A shared parameter is copied into the vector on entry. There is one context for a function, not one for a block or for a turn of a loop, so functions made in a loop all see the local as it is when they are called. The nested function finds each context it was made with in the function object it is running as (`invokee`), and keeps it in a local of its own; a function nested deeper is handed the contexts it needs from those.
- The places in a context are given out when the nested function has been read, to the locals it used, in the order of the reference's tables of locals (see the finding on that order), innermost scope first. Place 1 is kept for the method's `self`, so locals start at 2.
- A function between a local and a function nested two deep that uses it gets a context of its own that nothing is ever put in, with a place in it for each such local. The reference settles the middle function's view of the local too early, as if it were a local of the middle function. Hexicon makes the same useless vector.
- A function (not a method) in a method's code acts for the method's object. If the function might use `self`, the method puts `self` in place 1 of its context, and the function takes it from there on entry (`setself`). Any name that is not a local counts as a use, since it might be a property, and so does any string in double quotes. If the function uses `targetprop`, `targetobj`, `definingobj` or `inherited`, what is kept is all of what the method knows of its call (`storectx`, `loadctx`). An anonymous method shares locals in the same way, but its `self` is whatever object it is called on.
- A property whose value is an expression with such a function in it is made a method when it is read, not when its value turns out not to be a constant, because the context has to be made by something. Which of `self` or the whole of the call's context that method keeps depends, in the reference, on the function or method that happens to come before the property in the source: the parser's note of the body it is in is left over from there. A function in the property's value does not see that note, and takes `self` alone. Hexicon does the same.
- `return` cannot be followed by `{`: the reference takes a brace there for a mistake before it looks for an expression, so a short anonymous function has to be in parentheses to be returned. An expression statement cannot start with one either, since a brace starts a block.
- In `{x: ...}` a colon after a parameter's name ends the list, unless a comma or another colon follows, when it marks a named parameter. A parameter with a type and `multimethod` are not allowed in an anonymous function's list.
- The reference has two messages under the number of the error for a missing `}` at the end of a short anonymous function, and finds the other one: the message is "semicolon is not allowed in a short-form anonymous function", whatever is there. When the source ends there, the statement the function is in is given up on.
- When an initial value in a `local` statement cannot be read, the reference still looks at what follows it, and says that a comma or a semicolon was expected, before it gives the statement up.
- A statement with a `function` or `method` body in it is taken to start where the last statement inside that body started: the parser's note of where the statement it is reading began is not put back when the body is done. It shows in the line of a warning about the statement, such as that it cannot be reached.
- Whether a short anonymous function returns its expression's value is settled as it is read: it does unless the expression is a string to display or a call to a function already known to return nothing.
- When the source ends inside nested short anonymous functions, each one reports its missing brace in turn. When a property's value cannot be read at all, which is the source ending in it, the reference stops reading the source there and then; Hexicon went on to say that a property name was missing, and no longer does. Programs with these functions were cut off at 300 random places and compiled with both compilers (`tools/compile-tests/gen-truncated.py` makes such programs): nothing hung, and after these two fixes the messages were all the same.
- A parameter that can be left out (`count?`, `count = 1`) and a parameter passed by name (`count:`, `count:?`, `count: = 1`) are not parameters to the virtual machine. Each is a local, and the function fills it in as it starts, after the list of its extra arguments is made and before a nested function's contexts are fetched. The function's header counts the parameters that have to be there and, apart from them, the optional ones passed by position; parameters passed by name are in neither count. An optional parameter is filled in by comparing its place in the list with the number of arguments (`getargc`) and calling `getArg` if the argument is there; a parameter passed by name by calling `t3GetNamedArg` with its name, and with `nil` or a constant default value as a second argument if it has one. A default value that is not a constant is only worked out if it is needed: `t3GetNamedArg` is called with the name alone, and the error it throws when there is no such argument is caught by an entry the compiler adds to the function's table of exception handlers. Those two functions have to have been declared, as the system's headers do; without them the reference says that optional or named parameters need them.
- The parameters without default values are filled in first, in the order of the reference's table of locals (see the finding on that order), and then those with default values, in the order they were written, since a default value can use the parameters before it.
- A default value is not folded as other expressions are once every name is known. It was folded as far as it could be when it was read, so `1 + 2` is `3`, but a name that turns out to be an object is still a name when code is generated: `[obj, 1]` is built when the function starts, not kept as a constant list, and a parameter passed by name whose default value is an object's name counts as having a default that is not a constant, and gets the handler. Hexicon looks the names up when it generates the value and does nothing else to it.
- In a call, an argument can be passed by name (`f(1, count: 3)`). Arguments passed by name are worked out before the others, the last first, and go on the stack under them. The call's instruction counts only the arguments passed by position, and is followed by `namedargptr`, which says how many were passed by name and where their names are; that instruction is written after every kind of call, a property read with no other arguments included (`obj.prop(count: 3)` is `getprop` and `namedargptr`). The names of each call are in a table after the function's code (`namedargtab`), the tables of the latest calls first, and in each table the name of the last argument first.
- The reference stops with a memory fault when a parameter that is optional or passed by name has the name of a parameter before it (`f(a, a?)`): it reports that the local is defined more than once and then uses the local it did not make. Hexicon reports the same and reads on. This is an accepted difference.
- A message about the start of a function, which is where the two built-in functions are found missing, is given the place of the last statement generated before it, since nothing sets a place for a function's start: the last statement of the function before, or for a method, the place the method's property was given. Before any statement has been generated it has no place at all, and is printed without a file or a line. A method's property is given the place where the last statement read started, which is the last statement in the method's body if it has one, and the method's own first line otherwise.
- The list a `[rest]` parameter collects starts after the parameters that have to be there, so an argument for an optional parameter is in it too: with `f(a, b = 1, [rest])`, the call `f(1, 2, 3)` makes `rest` the list `[2, 3]`.
- Where an operand is missing, the reference carries on with an integer constant in its place, whose value is the integer value of the token it is then looking at. It never clears a token's integer value, so that is the value of the last number read, however long ago. It shows when the constant is used in something worked out while compiling: `[1, 2][` at the end of the source indexes the list by 2 and has nothing to say about the index, where `[1, 5][` reports an index out of range. Hexicon's tokens carry the last number in the same way. (Found by cutting the new test programs off at random places.)
- When a call's argument produces no value, the message numbers the argument by counting down from the number of arguments passed by position, over all the arguments, so with arguments passed by name in the call the number can be too small or less than one.
- `enum a, b;` makes each name a value of an enumeration, and `enum token` makes them kinds of token for a grammar as well. A name can be in several such statements. Like properties and objects, the values are numbered when the program is put together, from 1, in the order of the table of global names; since the names are known from the first reading of the source, a value can be used before the statement that declares it.
- The reference's comparison of two constants has no case for values of an enumeration, so when it folds `==` or `!=`, or takes an element out of a constant list with `-`, such a value is equal to nothing, itself included: `red == red` is `nil` and `red != red` is `true` when both sides are constants. The same comparison made when the program runs, through a local, is right. Hexicon folds them as the reference does.
- `prop = static expr` has the value worked out once, before the program starts. If the expression is a constant when names have been looked up, `static` means nothing and the property is the constant. Otherwise the value is a method that evaluates the expression (or pushes `nil` if it leaves no value), stores the result in the property of `self` with `setpropself`, and returns it. The method's code is not with the rest of the code: such code is kept apart, in the order it is generated, and goes in the image after all the other code, starting on a page of its own, with the function that sets up multi-methods after it. The image's list of static initializers has the object and the property for each, in the same order.
- When a static property's value has an anonymous function in it that needs a context, the property was made a method as soon as it was read (see the finding on such properties), and the reference then forgets that it is static: its code is with the ordinary code and it is not in the list of initializers. It is still the code of a static initializer, so the value is worked out the first time the property is asked for, when the method replaces itself with the result. Hexicon does the same.
- `name(args) = { ... }` in an object definition, the way an older version of the language wrote a method, is reported as "'=' is not allowed with a method definition", and the `=` is passed over.
- A name found to be undefined is noted as that, and said nothing more about; but it is not a property after that either. Using it later on the right of a `.` is an error ("symbol is not a property"), where a name never met before would be taken for a property with a warning.
- `replace` before a function's definition puts the definition in the place of the one there is, for which nothing is then generated. `modify` puts it in front: the old code stays, with no name, and `replaced` in the new definition is its address, or with arguments a call to it. A function nested in the new definition means the same by `replaced`. Either needs the same number of required parameters as the definition before, and the same answer to whether more are taken; optional parameters can differ.
- What `replaced` means is not settled when it is read. It is whatever the function it is in modifies when code is generated, so a later `replace` of the function leaves `replaced` meaning nothing in a function nested in the definition replaced, which is still generated though the definition is not, and is then an error. The number of arguments in a call to `replaced` is checked against the new definition's parameters, and the message names the function as `""`, the old code having no name.
- The reference cannot put together a program in which one function is modified twice in the same source file: it compiles the source, and then fails reading back the object file it has just written, with "invalid symbol type in object file". Hexicon compiles such a program, each definition reaching the one before with `replaced`. This is an accepted difference, of a kind with the reference's crashes: the reference has no image to compare with.
- `replace` or `modify` of a function with no definition before it in the source is not found out until the reference puts the program together, since the first reading of the source has made the name known: the message then is that a modified or replaced function was found in the object file before its original definition, and it names the object file. Hexicon writes no object file, and gives the name the file would have, without a folder; `compile-compare.sh` takes the folder out of the reference's message. If the function's own definition comes later in the source, that is an error where it stands, as a function defined twice. For an object the first reading does not pass on a name that only `replace` or `modify` gave it, so it is an error at once ("replace/modify cannot be used with an object not previously defined").
- `replace` of an object is a new definition, with its own superclasses, in place of the old one, for which nothing is generated. `modify name` has no superclasses: the definition there is becomes an object of its own, a class whatever it was before, with a new number and no name, and the new definition, which keeps the name and the number, has it as its only superclass. So what the new definition leaves alone is inherited, and `inherited` in a new method reaches the old one. A `modify` definition is a class if the definition it modifies was one, and is not given the property that says where an object comes in the source. `replace` before a property in a `modify` takes the property out of every definition the new one stands in front of, down to the first.
- The objects `modify` leaves behind are numbered when the program is put together, with the object they belong to: the first definition first, then each `modify` in turn, and last the number the name has. Objects with no name still come after all the named ones.
- `modify` of a class built into the virtual machine does not change the class. What the program adds is kept in objects of a kind of their own (`int-class-mod`), in a block of the image after the program's objects: for each class, one that is empty, and then one for each `modify`, whose only superclass is the one before. The object that stands for the class names the latest of them, and the virtual machine looks there for a property the class does not have itself. The empty one is generated after everything else in the program, with the anonymous functions. These objects are numbered just after the object that stands for their class, the empty one first. A property the class has natively, or a class it is a kind of has, cannot be given a value this way.
- `extern function name(params);` declares a function, and `extern object name;` or `extern class name;` an object, that is defined somewhere else. In a program of one source file that can only be further down the file, and for that the declaration is not needed, since the first reading has made every name known. What is declared, used, and never defined is found out when the program is put together ("unresolved external reference"), the functions and the objects together in the order of the table of global names; what is declared and never used is no trouble, and an object so declared has no number.
- `extern function name;` says nothing of the function's parameters. The first reading passes on what it knows of each function's parameters as the function's whole declaration, and what it knows is what was said first: so such a declaration ahead of a definition that has parameters makes the second reading take the definition for a different function ("incompatible previous declaration"). Hexicon does the same.
- `replace` or `modify` of an object that `extern` has declared, with no definition before it, is found out when the program is put together, as it is for a function, with the same kind of message.
- `transient` before an object's definition marks the object as one that is not saved or restored. In the image the transient objects are in a block of their own after the others, which says that is what they are. A `modify` is transient if the definition it modifies is. `transient` before a function or a class's template is an error; before `object template` it is passed over.
- An object template says what an object definition's leading values are: `object template 'name' "desc"? @location;` is for any object, and `Thing template ...;` for objects of a class. Each item is a kind of value and the property it is for: a string in single or double quotes holding the property's name, `[name]` for a list, or one of `@ + - * / % -> & ! ~ ,` and the name, for that token and then a value. `?` after an item makes it optional and `|` makes the next item an alternative to it; alternatives are optional all together or not at all. A property can come twice in a template only as alternatives of one group.
- `inherited` in a class's template stands for the templates the class gets from its superclasses: the template is defined once for each template of each superclass, nearest first, once for each template any object can use, and once with nothing in the place of `inherited`. It is worked out when the template is read, from what is known then. In a template that is for any object the reference stops with a memory fault; Hexicon defines it with the templates any object can use and with nothing.
- The values at the start of an object definition are read before any template is looked for: a string in single quotes is a single operand, one in double quotes is a whole expression (so `"desc" [1, 2]` is the string indexed, which is an error), a list is a list, and after an operator comes a single operand. The template is then looked for among those of the object's classes, in the order they are named, and each class's superclasses when it has none that fits; of two classes that each lead to one, the later is preferred only if it is a kind of the earlier. Only if the classes have none is a template for any object looked for. A class that is known only from `extern` might have templates nobody here knows, so nothing fits ("cannot use template with an unimported extern class as superclass"). Values that fit no template are reported when the object is generated, not when it is read.
- The properties a template gives values to come before the property that says where the object is in the source, and all of them are taken to be at the place of the first token after the values. A `modify` cannot use its class's templates, having no superclass anyone can name, only those for any object.
- `+ property name;` says which property `+` signs give a value to. An object with N signs before it (`++` counts for two) gets, for that property, the last definition read that had N - 1 signs, as the first of its properties; a value the source writes for the property takes its place. With no such property, or no such definition, the object is reported ("too many '+' signs") and has no value. After the signs can come `class` or `transient`, and the object needs no name.
- What is remembered for each number of signs is a definition, and it stays remembered when a definition with fewer signs comes along: after `a; + b; c;`, a `++ d` is still in `b`. A class is remembered only if it has signs itself, and an object that is a property's value never. A `modify` is a definition with no signs like any other; and an object put under a definition that has been modified since is in the object the `modify` left behind, not the one that now has the name.
- A definition with `+` signs whose name is not a name at all (`+ 5;`) makes an object named by the token. The reference keeps, for the name of such an object, only the place in the line it was read from, which later lines overwrite, so whether a second one is "already defined" depends on what the source says afterwards. Hexicon keeps the name.
- A property's value can be an object written in place: `prop: Class { ... }`, with template values before the brace or just inside it. The object has no name; it gets its number when the colon is read, is generated after everything at the outermost level, with the anonymous functions, in the order they were finished, and knows where it comes in the source like any other. It gets one more property, `lexicalParent`, the object it is written in, which it cannot define itself, though an ordinary object can have a property of that name. `replace` before the property applies to the property and not to what is inside the object, and the groups of properties open around it do not apply inside it.
- When a definition is found to have ended without saying so inside objects written in place, however deep, the place reported is where the outermost definition's property started, and every object being read ends there.
- `propertyset 'pattern' { ... }` in an object's properties groups properties whose names are the pattern with the name written in place of its `*`. The pattern has to be the characters of a name and exactly one `*`. Groups can be inside groups, ten deep, and the innermost pattern is applied first; a name that would be longer than 80 characters is reported and left as far as it got. A semicolon inside a group is passed over, even in an object that has no braces, and a definition whose end is missing inside one is said to be missing its brace. A property in a group can be a value, a method, or an object written in place.
- A group can have parameters, `propertyset 'pattern' (actor, *, extra) { ... }`, with exactly one `*`: each method in the group gets the group's parameters around its own, which go where the `*` is; with groups inside groups, the outer group's are outermost. The reference makes the combined list in a variable of a function that has returned by the time the list is read, and stops with a memory fault on the first method in such a group, with or without parameters of its own. Hexicon reads the method with the parameters meant, so that it makes the same image as the method written out in full. Values in such a group are no trouble to either. Where the reference's way of putting the list together would leave out a comma or put one too many (a group with nothing after its `*` inside one with nothing before), Hexicon puts in the commas that are needed.
- A method can stand for an operator: `operator +(other) { ... }` in an object's properties, with `+ - * / % ^ << >> >>> ~ | &`, `negate`, `[]` or `[]=` after the word. Each is a property every program has, named by the two words (`operator +`), and the virtual machine calls it when the operator is used on the object; `&operator +` is the property's address. The method has the operator's operands for parameters, but for the first, which is the object: one for most, none for `~` and `negate`, two for `[]=`. That is checked when the method has been read, so a mistake is reported where the next thing starts; a parameter that can be left out does not count, and a list of the rest is never right. A value given with `=` is not checked at all.
- An operator there is no method for (`operator ==`, `operator foo`) is reported, and the property defined is one named `unknown_operator`, like any property the source might name; so a second such mistake in one object is also "already defined". An operator's method in a `propertyset` is reported and defined all the same, under its own name.
- `delegated target.prop(args)` runs the target's method with the `self` of the method that says it, so it needs a `self`. The target is a single operand: a `.` or an argument list after it belongs to `delegated`, so `delegated self.helper.greet()` delegates `helper` to `self` and calls `greet` on what that gives, and a target that has to be worked out goes in parentheses or in a property named alone. With no property (`delegated target(args)`) it is the property being run. The code is the target, then `DELEGATE` with the property's number, or `PTRDELEGATE` with the property on the stack.
- `argcount` is how many arguments the function running was called with, and is one instruction (`GETARGC`). It can be used anywhere there is code.
- The order of an image's blocks: `ENTP`, `SYMD`, `FNSD`, `MCLD`, the code pool (`CPDF` and its `CPPG` pages), the constant pool, the objects, `SINI`, and `EOF`. Even a program of two functions has nine metaclasses in `MCLD` and 21 exported symbols in `SYMD` (`LastProp`, `Constructor`, `Destructor`, the three grammar properties, and one for each operator that can be overloaded).
- A pool's page size is the smallest power of two, from 2,048 up, that holds the pool's largest item. Items are laid out in the order they were generated, and one that does not fit in what is left of a page starts the next. Code has two streams, main and static; the static stream starts on a new page. It is never empty: the compiler always generates a function there for registering multi-methods, which is a bare `retnil` when there are none. The constant pool's pages are stored XORed with a mask (0xDF from `t3make`).
- A compiled function is a 10-byte header (parameter count, with the top bit for variable arguments; optional parameter count; number of locals; stack slots needed, locals included; offset of the exception table; offset of the debug table), the code, the exception table if any, and the debug table. The stack figure comes from counting pushes and pops as the code is generated, not from analyzing it afterward.
- A function has a debug table even when the program is not compiled for debugging, if it has any local variables or parameters: the table then has no line records, only the frames of local names. A name of one or two characters is stored in the table; a longer one is stored in the constant pool, once per name for the whole program, and the table has its address. The locals of a frame are written in the order the reference's hash table gives them, which is by the sum of the name's bytes modulo the table size, and within one sum, the most recently defined first. Hexicon has to order them the same way.
- The peephole rules look at the last instruction written, or the last two, and rewrite in place. They are ported one for one. Two discards become a `disc1 2`, but a third is not added to it: three in a row are a `disc1 2` and a `disc`. A label resets what the rules remember, since a jump can arrive there.
- At the end of a function, a `retnil` is added unless the last instruction cannot be fallen out of (a return, a throw, or a jump). Then jumps to jumps are shortened.
- The reference's driver for testing expressions alone is no use (see above), and its whole-program test driver compiles for debugging, which `t3make` by default does not. `t3make` is the one to compare with.

Open after the first part of milestone 3:

- A number with a point or an exponent, and an integer too large for 32 bits, in whatever radix it is written, is kept by the compiler as its text. When code is generated it becomes an object of the class `BigNumber`, with as many digits as the text has, and each place the constant is used gets an object of its own; so does each element of a constant list and each property's value. The objects are numbered after all the others, in the order the code that uses them is generated, and go in a block of their own after the program's objects. If the program has not declared the class, the image says it depends on `bignumber/000000`, just before `intrinsic-class`.
- An integer too large to be one is reported with a warning, where its object is made, so once for each use and not at all if it is never used. Arithmetic that brings such a number back in range makes it an integer again: `4294967296 - 4294967295` is the integer 1, and `-2147483648` is an integer though `2147483648` is not. A number written with a point never becomes an integer.
- A constant sum or difference of integers that overflows is worked out again as numbers that are not integers, and stays one. A product wraps (see the finding on that). A quotient is taken to overflow when the lowest integer is divided by 1, which it does not, and not when it is divided by -1, which it does and which stops the reference; Hexicon gives the lowest integer for the second.
- Arithmetic on constants that are not both integers is done with the virtual machine's own arithmetic: each operand has the digits its text has, an integer ten, and the result has as many as the operand with more. It is then written out as text in full, with a point at the end if it is whole, and read again when it is next used. `+ - * / %` and the comparisons work; the operators on bits and the shifts are reported ("floating point values can't be used with this operator") and leave the left operand as the result.
- A constant division that is not of two integers is, in the reference, only the whole part of the quotient: `1 / 3.0` is 0 and `10.0 / 4` is 2, though the same division done by the program when it runs gives 0.3333 and 2.5. The reference asks its arithmetic for the remainder as well as the quotient, and a division asked for a remainder stops at the point. Hexicon does not follow it (decided 2026-11-20): a constant quotient is the one the program would get, so a program with such a division compiles to a different image, and the tests that are compared with the reference have none. An integer too large to be one that a division leaves with a fraction is not made an integer again.
- A number that is not an integer is true unless it is zero. Added to a constant string it is its text as written, so `'x' + 1.50` is `'x1.50'`, and the text arithmetic wrote, so `'x' + (1.5 + 1.5)` is `'x3.'`. `-` before one puts a minus sign before the text or takes one away.
- The fifth byte of a number's data in the image has the sign and the kind of number in its low bits. The reference never sets the other bits when it reads a number from text, so they are as its memory had them; Hexicon writes zeros.
- `R'...'` or `R"..."` is a regular expression: an object of the class `RexPattern` whose data is the address of the text in the constants. Like a number, each use makes an object, numbered in the same sequence, and the objects go in a block after the numbers'. The image depends on `regex-pattern/000000` if the program has not declared the class. As a constant it is equal to nothing, cannot be added to a string by the compiler, and cannot be indexed.
- A list with `->` between elements is a lookup table's: `[key -> value, key -> value, * -> default]`. Every pair has to have its arrow, and the default, if there is one, comes last; a list that breaks the rule is reported by the place in it, counted as a message counts ("after 2nd element"), and a nil is put in to keep the pairs in step. The code makes a list of the keys and values in turn, with the default at the end, and then a `LookupTable` from the list. The list is made when the program runs even if everything in it is a constant, so such a list is never a constant itself: it cannot be a `case`, and as a property's value it is code.
- For each `<<one of>>` or `<<first time>>` the compiler defines an object with no name, of the class `OneOfIndexGen`, when it has read the whole construct, so one inside another gets the lower number. The object has two properties, `numItems`, the number of alternatives, and `listAttrs`, a string that says how to choose (`rand`, `seq,stop`, `shuffle` and so on, from the words that end the construct; `rand` with none), and no note of where it comes in the source. It is generated after everything at the outermost level. The first reading defines nothing, so the two property names are not known until the second.
- The code asks the object for `getNextIndex()`. If every alternative is a constant, they are a constant list and the answer indexes it. If not, as always in a string in double quotes, the answer goes to a `SWITCH` with a case for each alternative, numbered from 1, and nil for any other answer. `getNextIndex` has to be a property; if it is nothing, it becomes one without a word.
- `dictionary name;` makes a dictionary, an object of a class built into the virtual machine, and makes it the one that the words of the objects defined from there on go in, until another such statement; naming a dictionary again makes it current again. `dictionary property noun, adjective;` makes the properties dictionary properties from there on in the source: on each reading, a value given before the statement is an ordinary one.
- A dictionary property's value in an object is one or more strings in single quotes, one after another with nothing between (`noun = 'lamp' 'lantern'`). Anything else is reported ("vocabulary property requires string value"), and so is a method, an object written in place, or a place in a template for such a property; words with no dictionary current are reported too. The strings are the object's words for the property.
- Every object defined once there are dictionary properties gets each of them, with or without words, so that it can have the words of its classes. What the property's value is, is settled when the program is put together: a list of the object's words for it, and if there are none the property is taken out. An object written in place inside another makes the reference forget which of them the outer object had given words for, so the outer object gets those properties a second time; it comes to the same value.
- When the program is put together the reference goes through its table of global names, chain by chain and in a chain the object with the highest number first, and then through the objects with no names in the order they were made. Each object that is not a class takes its classes' words, each class taking its own classes' first, one word at a time in front of what it has; so an object's words are its last class's backward, and so on to its first's, and then its own in the order written. Then its words go in its dictionary, and its dictionary properties get their lists. A class's turn does not give it its classes' words; it has them only if some object of its kind has had its turn first, which is a matter of names and numbers. Hexicon follows all of this.
- A definition that `modify` set aside is in that table under a name made of its number, and has its turn like any object: if it was an object and not a class, its words are in the dictionary as its own, under its own number. `replace` before a dictionary property takes the property's words away from the definitions modified. A definition that takes another's place with `replace` keeps the words the other had.
- A dictionary in the image is its number, four bytes for the object that will compare words when the program runs, which is nothing yet, and its words: each is its length, its text with every byte exclusive-ored with 0xBD, and each object and property it is a word for. The words are in 128 chains by the sum of their letters as capitals, the newest first in a chain, and a word's uses are the newest first; the same use is there once. The dictionaries are in a block of their own after the program's objects, in the order of their numbers, with their sizes in four bytes.
- A dictionary is numbered when its turn comes in the table of names, or just before the first object in the table whose words go in it, if that is earlier: the reference writes it out ahead of that object, and numbers things as it reads them back.
- The lists of words go at the end of the constants. A word's text is there once for all the lists, but the reference no longer knows what strings the program's code put in the constants, so a word that is also a string in the program is there again.
- A dictionary's name in an expression is not a constant to the compiler: it is pushed as an object, and a list with one in it is made when the program runs. It cannot be the operand of `new`, modified or replaced; nothing stops an object being defined with one for a superclass.
- `dictionary name;` where the name is already something else is reported, and the reference then stops with a memory fault. Hexicon goes on.
- With more than one dictionary the reference can put an object's words in the wrong one. It numbers the dictionaries twice, once in the order their objects are written out and once in the order they are read back, and the two differ when a dictionary's own place in the table of names comes before the first object that uses another. Hexicon puts each object's words in the dictionary that was current when it was defined (decided 2026-11-21); a program with one dictionary, which is every game there is, compiles to the same image either way.
- `grammar name(tag): tokens : Superclass properties ;` does two things. It names a grammar production, an object of a class built into the virtual machine, which is made if the name is nothing yet; and it defines a class, the object made when the tokens are matched. With a tag the class has a name, `name(tag)` with the parentheses in it, which no expression can say but `modify grammar name(tag)` and `replace grammar name(tag)` can; without one it has none. `grammar name;` only declares the production. A name in the tokens that is nothing becomes a production too, but only on the second reading; the first passes it over.
- The tokens are rows separated by `|`, and parentheses group alternatives inside a row. They are read twice. First everything up to the colon is taken apart into rows, a row written out for every choice among its groups, the first group's choices changing fastest; then those rows, with `|` between them, are read in place of what was written, and the colon after them. So `('a' | 'b') 'c'` is two ways of making the phrase up, `'a' 'c'` and `'b' 'c'`, and an arrow after a group is a mistake.
- In a row, a string is a word to match as written; a property, any word the dictionary has for it; `<noun adjective>`, a word for any of several; an object, which has to be a production, a phrase of it; a value of an enumeration declared with `enum token`, a token of that kind; and `*`, which has to come last, whatever is left. `-> prop` after any of them but `*` keeps the match in the property. `[badness n]` before the rest says how much worse the row is than another, with a constant integer.
- A mistake in `[...]` makes the reference pass over the rest of the statement and more: it means to stop at the `]`, but its loop only leaves at a semicolon or a brace, and it is then run a second time. Hexicon follows it.
- The class gets two properties after its own: `grammarInfo`, a list of its name (with the tag) and the values of the properties its rows give matches to, which is a constant list if there are none and code otherwise; and `grammarTag`, the tag as a string, or an empty string. A `modify` with nothing between the colons keeps the rows there were, and still gets the two properties, so its `grammarInfo` is the name alone.
- The rows of a statement with no tag belong to the production at once. Those of a statement with a tag are kept with the class's name until the program is put together, so that `modify grammar` and `replace grammar` can change them; then each class's rows are added to its production's, in the order of the table of global names. In the image a production is its number and its rows: for each a score that is always zero, the badness, the class, and the things to match, each as the property the match is kept in, a kind, and what the kind needs. The productions are in a block after the dictionaries, in the order their names were first met.
- Each word in a row goes in the dictionary that was current when the row was read, as a word for the production by the property `miscVocab`. These go in before any object's words.
- A production with no rows that no `grammar name;` declared is reported when the image is put together, with no place in the source ("grammar production has no alternatives defined"): it is most likely a name spelled wrong in a row. It is not reported if anything else was found wrong at that stage, such as a function declared and never defined.
- A production's name in an expression is like a dictionary's: an object that is not a constant to the compiler, that cannot be the operand of `new`, modified or replaced.
- `object: Superclasses { properties }` in an expression, or `object { properties }`, is an object made each time the expression is evaluated. It has no name, takes no template values, gets none of the properties the compiler gives other objects, and puts no words in a dictionary. The code makes the object with `TadsObject.createInstanceOf(superclasses)`, which runs no constructor, sets each property on it in turn, and then calls its own `construct()` if it has one; the object is left on the stack whether it is wanted or not. The program has to have declared `TadsObject` with `createInstanceOf` and `setMethod`, as the system headers do.
- A property of such an object is one of three things. A method is an anonymous method, which shares the locals of the code the object is written in, and is bound to the object with `setMethod`. A value is read as the body of an anonymous method too, so that it is worked out each time the property is asked for and can use the same locals; but if it turns out to be a constant it is set on the object outright and the method is dropped, and if it is text to display the text is bound with `setMethod`. A value marked `static`, or an object written inside this one, is worked out once when the object is made and set outright. An object written inside gets a `lexicalParent` that is no object at all, since the one it is written in has no number.
- The reference tells what kind of body it is reading by whether the word before it was `method`, which before a method of such an object it is not. So the method's body is read as an anonymous function's: if it uses `self`, it asks for the context of the code around it, and the code that makes the object passes one, though that code may have none (it passes whatever its first local is) and the method, being a method, uses the `self` it is called with. Hexicon generates the same code.
- A superclass of such an object that is not an object's name stops the reference with a memory fault when code is generated. Hexicon reports it as an undefined symbol.
- `defined(name)` is true if the name means anything in the program and nil if not, and `__objref(name)` is the object if the name is one's and nil otherwise; `__objref(name, warn)` and `__objref(name, error)` also say so when it is not. The name can be a local's, and is still asked about as a name of the program's. Each is a constant, but one that a condition can be made of without the warning that the condition is always true or always false. They are answered where they are read, from what is known then: on the second reading that is every function, object and property the first reading found.
- A function whose parameters have types, `put(Thing a, Box b)`, is one version of a multi-method. A type is a name before the parameter's name, an object's or a built-in class's; a name that is nothing yet is taken for an object defined somewhere else. `multimethod` after the parameter list makes a function a version though no parameter has a type. Only a function can have such parameters, not a method of an object or an anonymous function. A version's name in the table of names is the multi-method's, `*`, and each parameter's type, or nothing, with `;` after it, and `...;` at the end if it takes more: `put*Thing;Box;`. `replace` and `modify` work on a version by its types.
- The name the source uses, `put`, is the multi-method itself: a function declared, the first time a version is read, as taking any arguments and defined nowhere. A function of that name with no types is then a different declaration and is refused, and so is a version of a name that is already an ordinary function.
- A call to a multi-method is a call to the library: the arguments are made into a list, and `_multiMethodCall` is called with the list and the multi-method. (With arguments spread from a list, `put(args...)`, the reference leaves out the instruction that makes the list, and what it writes is not code; Hexicon puts the instruction in.) `inherited(args)` in a version calls `_multiMethodCallInherited` with the version and the arguments, for the library to find the next version that fits; `inherited<Thing, *, ...>(args)` calls the version for those types outright, `*` being a parameter with no type.
- When the program is put together the compiler writes two more pieces of code. After all the rest, in the order of the table of names, each multi-method gets its own function, which takes any arguments and calls `_multiMethodCall` with them and itself, so that a multi-method's address can be taken and called. And among the code that runs before the program starts there is a function that calls `_multiMethodRegister` for each version, in the order of the table, with a list of the version's types (nil for none, the string `'...'` for more), the version, and the multi-method, and then calls `_multiMethodBuildBindings`. That function is there even when there are no multi-methods, when it only returns. If there are any, an object is made after all the others with that function as its one property, which is what gets it run: it is first in the image's list of what to run before the program starts, ahead of the code for static properties.
- The library keeps what it knows in properties of the types, so a built-in class used as a type, and `Object` for a parameter with no type, is given an empty object to hold what is added to it, if it has none.
- The four library functions have to be defined (the system library's `multmeth.t` has them). `_multiMethodCall` used and not defined is an unresolved reference like any function; otherwise a missing one is reported when the image is put together ("library support function ... is missing or invalid"). A version that is only declared, with `extern`, and never defined is not in the program at all: the library is not told of it, and nothing is reported.
- A program of several source files is put together in three steps, as the reference does it, though Hexicon writes none of the reference's files. First each file is read for what it defines (the reference's symbol file). Then each is compiled knowing what all the files define, its own included: the names are read in, file by file in the order of the files, before any of the file's source. The first file to define a name has it; but a name that is a property only because its address was taken gives way to anything else. A dictionary or a grammar production can be defined in any number of files. Last, what was generated for each file (the reference's object file) is read into one program, in the order of the files.
- In a compiled file, objects, properties, and the values of enumerations have numbers of the file's own. The numbers they have in the image are given as the files are read into the program: each name gets the next number the first time a file that has it is read. A file has a name if it defines it, or if it uses it. So the numbers depend on the order of the names in each file, which is the order of the table of names the compiler had when it finished with the file: chain by chain (a name's chain is the sum of its bytes, in 512), and in a chain the name that went in last comes first. The names from the other files went in before any the file's own source added, each file's in the order of its table.
- Whether a file uses a name is whether the reference ever looked the name up while it compiled the file. Reading the names in counts: a name that two files both make known, as a property that both use is, has been looked up in every file by the time the second is read, and so every file has it, whether its source mentions it or not. `extern object name;` on its own is no use of the name.
- An object's dictionary is read just before the object, if the file has not had it yet. The definitions that `modify` set aside in the same file are numbered just before the object, the oldest first, and they stay objects of the program even if a `replace` of the object comes after. A built-in class's name brings the properties the class declares, which get numbers then if they have none, and the objects that hold what the file adds to the class. After the names come the file's objects with no names, in the order they were made, and then the objects that its constants were made into.
- What each file adds to a built-in class with `modify` is a chain of objects: an empty one, and one for each `modify`. A later file's chain goes on top of an earlier file's: its first object with anything in it gets the earlier file's last for its superclass, and its empty one is left in the image with nothing above it.
- The code and the constants of the files follow one another in the image in the order of the files, and a string that two files both have is there twice. The dictionaries, the lists of an object's words, the grammar productions, the code for multi-methods, and the names of locals are made when the files have all been read, from all of them together, and come after.
- The tables the reference goes through when the program is whole are in the order the names went into the program: so what is unresolved, and the multi-methods and their versions, come out chain by chain, and in a chain the name read last first. Within one file that is the reverse of the order of the file's own table.
- Two files that define the same function or object: "symbol \"f\" (type: function) redefined in object file \"b.t3o\"", naming the object file the reference would have written for the second, and with both kinds if they differ. But a file that defines as one kind of thing a name an earlier file's first reading made known as another is told so when it is compiled, like a second definition in one file.
- The sets of built-in functions and the built-in classes each file declares have to come in the same order in all of them, since a call to a built-in function is compiled as a place in the list of sets. They do, as long as the files include the same headers in the same order, because each file starts with the lists of all the files before it reads its own source. Otherwise: "conflicting intrinsic function set".
- A project is read as the reference's `t3make` reads its command line: the options, and then the modules, each a source or a library (`-source name`, `-lib name`, or a name, which is a library if it ends in `.tl`). A project file (`-f`) is read after the whole command line, as more of it, so what the project file says comes later and wins: `-pre` in a project file undoes `-nopre` before it on the command line, and `-o` there names the image. Each word of a project file is an argument, or a phrase in quotes with a quote in it stuttered (`""`); a line that starts with `#` is a comment, and everything from a `[Config:...]` line on is the development system's. What a project file names is relative to the folder it is in.
- A library's lines are `name:`, `source:`, `library:`, `resource:`, `needmacro:`, and `nodef`. What a library names is relative to its own folder, written with `/`, and becomes a path with the system's separator; and the library's folder is searched for included files, after the folders before it and before the system's headers. `$(NAME)` is the value the last `-D` or `-U` before the library gave the macro, and `$$` is a dollar sign; an undefined name and a `$` with anything else after it are reported, and the line used as it comes out. Only a library that cannot be opened, a line with no colon, or a line too long stops the build: an unknown definition, an undefined name, and a `needmacro:` whose macro is undefined are said and the build goes on. The messages name the library and the line, `mylib\sub\sublib.tl (2): missing colon`, and a library that cannot be opened is said with no `error:` in front.
- A source or library is found where its name says, or else along the folders of `-Fs`, then `TADSLIB`, then the system library. A name without an extension has `.t` or `.tl` added. `-x name` after a library leaves out the source the library calls that (`en_us/en_us/en_us` for a source in a library in a library), which still counts in the modules' numbering. No two modules can have one name, whatever their folders, as their object files would be one file: "module \"b\\main.t\" the has same name as an existing module" (the reference's words), or "... has the same name as an existing module from library \"...\""; for the system library's `_main`, the reference has no library name, and says `(null)`.
- `-D NAME` with no value defines the macro as nothing, where Hexicon had said `1`.
- The options that have to do with the reference's own files and progress are taken and do nothing (`-a`, `-al`, `-q`, `-nobanner`, `-Fy`, `-Fo`, `-FC`, `-errnum`, `-statprefix`, `-statpct`); `-v` lists the sources, as the reference's progress does, on lines that start with a tab. `-w0` drops the warnings, and `-we` writes no image if there are any; Hexicon still gives all the messages it would, where the reference stops at the first step of the build that has a warning. The options for what Hexicon does not do yet are refused as not supported: `-d`, `-c`, `-P`, `-Os`, `-Fa`, `-w2`, `-w+N` and `-w-N`, `-test`, `-clean`, and `-res`. Without `-nopre`, `hexicon build` says that it has not run the program before writing the image.
- When an object file is found wrong as the program is put together, the reference reads the rest and stops there: nothing is said of what is unresolved or of `_main`.
- The reference reads every module's symbol file before it compiles any module, and looking up a name it reads a second time counts as a use of what the name already was, if that is an object, a property, or a value of an enumeration; its other kinds of name, the built-in classes and the functions, take no notice. And the module that has a `replace` or `modify` of something only declared in it, from a template or with `extern`, does not make the name known in its symbol file: the module that defines it does. Both decide which modules have which names in their object files, and so the numbers of objects.
- `#pragma sourceTextGroup(on)`, or `#pragma sourceTextGroup` alone, gives every object that is not a class or a `modify`, from there to `(off)`, a property `sourceTextGroup` after `sourceTextOrder`: an object of the compiler's that stands for the source file. That object is made the first time the pragma turns the groups on in a file, with `sourceTextGroupName`, the module's name as the project gave it (`start`, or `actions` for a library's source), and `sourceTextGroupOrder`, its place among the modules of the build, from 1. `-Gstg` turns the groups on from the start of every file. adv3Lite uses this.
- `rand(a, b, c)`, with two or more arguments and none of them a list spread out, is not a call with those arguments: `rand(3)` chooses, and a switch on the result evaluates only the argument chosen, from 0 for the first, with nil if the number is none of them. So the arguments can be double-quoted strings, which are displayed. The cases are written last first. This is any call of a name `rand` that has not become a constant: the built-in function, or a local of that name, but not a function of the program's.
- `&tadsSay` is a pointer to the built-in function, by its place in its set and the set's number.
- `method name(...) { ... }` at the outermost level is a function whose code has a `self`: the object it is called as a method of, after `setMethod` gives it to one.
- `x is in (...)` and `x not in (...)` are truth values, like a comparison, so `a && x is in (...)` needs no conversion to one after it.
- `inherited` in the body of a version of a multi-method that a later `modify` has put another body in front of is still in that version: it calls the library with the version, as it is now.
- `modify` of an object that an earlier file defines is put together as it would be in one file. The definition there was becomes an object of its own, a class, with a new number, given just before the file's other numbers for the object; the object's number goes to the new definition, whose one superclass is the old; and the old definition's words are the new one's too, in front of its own. A property with `replace` before it is taken away from the definition there was and from any that one was itself in front of, words included.
- `replace` of an object that an earlier file defines takes the old object out of the image. Two things are left of it: the definitions that a `modify` in the earlier file had set aside, which stay in the image as classes that nothing is made from; and the object's own words, which are still its words, after the new ones. (The reference adds the new words to the list it has for the name, and nothing empties the list.)
- `replace` of a function that an earlier file defines takes the old function's code out of the image, with the code of any definitions `modify` had put it in front of. The names of the old function's locals stay in the constants. `modify` of a function leaves the old code in, as what `replaced` means in the new: a call or a reference to it goes to wherever the function was before this file changed it.
- The file with the second definition has to come after the file with the first. If it comes before: "modified or replaced object \"x\" found in object file \"a.t3o\" before original object definition was loaded", and then, when the later file is read, the object is a redefinition. For a function the reference gives the first message and stops with a memory fault when it reads the later file; Hexicon gives both messages.
- `Name template ...;` is no use of the class's name: a file that gives a class a template and makes nothing of the class does not have the class in its object file.
- The words in a grammar rule go in the dictionary that was current when the rule was read, but only from a source file that also defines some object while that dictionary is current: any object, with words or without, other than the nameless classes that `grammar` statements with no tag make. The reference gives a dictionary a place in the object file, which is what a rule refers to it by, only when it writes an object that has the dictionary; a rule in a file with no such object has lost its dictionary by the time the program is put together, and its words go nowhere. The same holds for a program of one file. Hexicon does the same.
- An object can end up with the same property twice (a dictionary property with a nested object after it in the same definition does it: the list of words is there twice). The image has an object's properties sorted by number, and which of two with the same number comes first is up to the sort the reference was built with. Hexicon keeps them in the order they were defined; the reference build here has them the other way about. Nothing can tell them apart when the program runs.
- A parameter's default value is compiled without its constants being worked out (see above), and one thing that follows is visible: in `b = (a ? f(a) : 2)`, where `f` returns nothing, the reference still knows `f` for a function there and gives the first branch the value nil. Anywhere else the function's name has become a constant by then, and a call through a constant is taken to return a value.
- The messages of the first reading of the source are kept and those of the second added, as the reference does, so a warning from the preprocessor comes out twice. That is the reference's behavior, and is not pleasant; Hexicon's own language may want it otherwise.
- Warnings that the reference gives only when asked for every warning (an unused parameter, for one) are not given at all.
- An image's exported symbols and metaclass list are the fixed ones of a program without `export` statements or `intrinsic class` declarations.
- The time stamp in an image, and `__DATE__` and `__TIME__`, are in UTC from `hexicon build`. The reference uses local time.
- Preinitialization is the reference's VM running the image inside `t3make`, in preinit mode, with no arguments for the program, and then writing the image anew from what the run left (`vm_rewrite_image`). `t3pre`, the reference's program that does only that, passes the program the name of the image it will write as its first argument, by an off-by-one in its own argument handling; `hexicon preinit` does the same, so the two can be compared.
- `t3GetGlobalSymbols()` during preinitialization is the linker's table of global names, in the order of its hash chains. It has names no source can write: each definition a `modify` set aside, and each object that holds what is added to a built-in class, is named by its number in hexadecimal after a space (`" 1a"`), and the object that sets up multi-methods is `<multiMethodInit>`.
- `t3GetGlobalSymbols(T3PreprocMacros)` is the table of macros the linker's preprocessor ends with. It starts with the compiler's own, and each object file adds the macros its source had defined at its end, as the source wrote them; a name the source ever undefined, or defined again differently, is left out of the object file. A macro two files define differently is in neither, unless a later file defines it again. `__LINE__` and `__FILE__` are there too, as `0` and nothing, since no source is being read.
- A library can keep these tables in the image: adv3Lite's debugging code keeps the table of macros. A program's image then has the system's name in it, from `__TADS_SYSTEM_NAME` and `__TADS_SYS_...`, which is `HEXICON` from Hexicon.

Open after milestone 1:

- In a message, a name with a character that is not ASCII is shown by the reference with its nearest ASCII stand-in (`cafe` for `café`). Hexicon shows the character's code instead.
- `#if` expressions are evaluated by a small evaluator of the preprocessor's own: integers, strings, `true`, `nil`, and the operators on them. The reference uses the compiler's expression parser and constant folding, which also covers floating-point numbers. The parser replaces the evaluator when it exists.
- The preprocessor's own comparison is with the reference's test program. The predefined macros and the default character set are now covered by the comparison of compiled programs instead.
- Speed has not been looked at. An argument is copied each time it is expanded.
